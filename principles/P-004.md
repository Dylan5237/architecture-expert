# P-004 Failure Containment ∝ Responsibility（故障遏制与责任相称）

## Statement
子系统的故障权力（blast radius，V-021-A）不应超过其职责与系统经济性所要求的范围；隔离边界（failure domain，静态分区结构）应按「可接受的最大同时损失」显式设计，而非按技术组件自然边界默认。

## Mechanism
故障沿共享资源与依赖传播（S-053：复杂系统故障是多因素耦合）。隔离把传播图切割，使单一故障的受影响面 ≤ 设计的 failure domain。cell/shard（S-050）、舱壁（S-047）、进程隔离（S-112 平台实例）都是把故障域显式化的机制。反例形态：防御机制自耦合（S-063：DNS 撤回 BGP 宣告是保护机制变成放大器）；自动 failover 的故障域大于预期（S-060 脑裂）。

## Protects
availability（局部故障不全局化）、reliability（V-005-B ISO 义）。

## Applies When
多租户/多用户共享系统；故障成本高的路径；存在共享瓶颈的系统。

## Does Not Necessarily Apply When
单用户单机工具：隔离的成本（多进程/多副本的协调开销）可能超过其保护价值——**「故障权力≤职责」是 graded heuristic 面而非绝对律**（Stage 1 已登记的证伪方向）；共享经济资源（共享 DB）有时是正确选择。

## Failure Patterns Explained
cascading failure（S-048 Ch.22）；noisy neighbor；split brain（S-060）；全局配置推送故障（S-059/S-064 内容更新绕过灰度）；恢复路径依赖被故障本身的资源（S-063）。

## Trade-offs / Costs
隔离的固定成本（每 cell 的容量冗余、运维单元数上升）；隔离边界错误导致的路由复杂度；故障域过小限制资源共享效率。

## Distinguish From
- bulkhead/circuit breaker 等 tactic（V-017-B；它们是实现隔离的机制，本候选是隔离量与职责相称的主张）；
- resilience vs fault tolerance（V-005-C/D：无全序——本候选不涉及强弱排序，只涉及故障域大小的设计）；
- P-003（有界性管单路径资源，本候选管跨子系统传播面）。

## Evidence
- S-047（empirical/heuristic）：bulkhead/stability patterns 出处；
- S-050（empirical）：cell-based/shuffled sharding 的 AWS 实践；
- S-061/S-063/S-060（empirical postmortem）：三起不同机制的故障域事故；
- S-053（theoretical）：复杂系统故障理论。
- 独立家族：模式专著 + 云厂商实践 + 事故实证 + 安全科学理论，四族。

## Cross-System-Shape Check
云/分布式（S-050/061/063）、单进程 Desktop（S-112 渲染进程崩溃不致命）、嵌入式（S-113 任务级无内存保护——注意 FreeRTOS 内核无进程隔离，隔离在嵌入式是弱化形态，须 scoped）。

## Counterexample / Falsification Plan
①寻找隔离成本明确超过收益的成熟系统（小团队 SaaS 过度 cell 化）；②检验「职责相称」如何度量——若不可操作化则本候选降级为 heuristic；③S-063 类「防御机制自耦合」是否构成对本候选的反例（隔离机制本身扩大故障域）还是其佐证。

## Open Questions
- blast radius 的可操作性度量（用户数？请求比例？数据面？）——CONTESTED 候选；
- 嵌入式形态的隔离弱化是否需独立词条——随 Stage 7 domain 层处理。
