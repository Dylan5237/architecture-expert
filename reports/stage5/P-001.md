# Dossier P-001 Explicit Ownership（final: NARROW）

## Candidate under attack
一切运行时实体与可变状态必须能回答「谁创建、谁可写、谁停止、谁清理、崩溃后怎样」（S-084/085/086/091/062）。

## 攻击与结果（final）

- **攻击 1：Erlang/OTP（S-114 修正后）**：supervised tree 是把 ownership 显式编码进架构的**合规机制**——反例不成立，但它证明的是「supervision 是合规机制模式」，**不是**「每个 Erlang process 都有 supervisor / runtime 禁止 unsupervised spawn」（该过强表述已从 S-114 删除，Akka.NET 无源泛化已移除）。
- **攻击 2：GC（S-116 修正后）**：GC 只豁免 **managed-heap reclamation** 维度的释放归属；不豁免任务/会话/外部句柄/副作用/可变业务状态的语义生命周期归属。GOMEMLIMIT 是 soft runtime memory budget 而非 hard process memory bound——「GC 免除了谁释放，没免除谁为总量负责」。
- **攻击 3：actor 邮箱（S-115 修正后）**：邮箱由接收进程拥有并消费——「ownership 缺失」论断撤回；**邮箱容量无界是资源维度问题，移交 P-003**。
- **GOOD CASE**：supervised daemon「无限运行」由 supervision + restart intensity 兜底，不得报生命周期缺失。

## D-* Results
- **D-06 DISTINCT**：权威清晰但实体无主 vs 归属清晰但语义未声明，案例对成立。
- **D-07 DISTINCT**：有 deadline 的 fire-and-forget（有界无主）vs scope-owned 但计算无界（有主无界）。取消/清理语义归 P-001，资源界限归 P-003。

## Candidate Disposition
**NARROW**

## Proposed Narrowed Statement（Stage 6 input）
运行时实体与可变状态的创建/修改/停止/清理必须有可回答的归属；豁免仅限运行时语义托管的资源回收维度（managed-heap reclamation）——总量责任与「谁能写」的裁决不在豁免内。supervision 是合规的 ownership 机制模式，不是普适 runtime invariant。
