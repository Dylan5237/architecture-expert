## Decision rationale

**Broken property.** The accepted exchange contract (PRODUCT_INTENT): every published length is in metres, the unit tag truthfully describes the number, and unconverted values must not be published as metres. The recipient is an independent consumer; the convention is fixed for this pass.

**Confirmed defect mechanism (CODE + TEST, CONFIRMED).** `publish()` asserts `unit: "metre"` unconditionally at the emit boundary, while the conversion decision is delegated to the profile. The legacy profile is a pass-through (returns the input number *and* input unit), so whenever selection routes to legacy, a non-metre number is emitted tagged `metre` — exactly the observed output class. The reproducer confirms the legacy path produces precisely this defect. GC gate: GC-009/GC-010 (governed break) don't apply — no governance record and the convention is explicitly fixed; GC-011 doesn't apply — this is an external independent consumer, not coordinated internals. MP-002 supports the fix placement: unit conversion is a variation axis deliberately hidden behind the profile, so the emit site may not assume which side of that axis was taken.

**Attribution to the vendor update: no — not yet (NEEDS_EVIDENCE).** Two candidate causes were both live in the reporting window (HISTORY, CONFIRMED coexistence, UNKNOWN per-output mapping). The legacy-profile mechanism is *demonstrated* to produce exactly this output; the vendor-update attribution is a bare USER_ASSERTION, still HYPOTHESIS, and nothing retained can ground it: the production output and history carry no source-unit declaration, selected profile, input identity, or adapter build identity, and no per-output revision mapping exists. That is a genuine FP-007 instance (not a telemetry-stack complaint — the specific attribution question is concrete, unanswered, and underivable). The incident note's guess stays CONTESTED; it is verification work, not KNOWLEDGE_DRIFT. Note the correction below is attribution-agnostic — it closes the lie under *either* cause — so further attribution does not change the decision.

**Minimum correction (vs. wider redesign).** Move unit provenance across the boundary: `normalise()` returns `{number, unit}` of what it actually produced, and `publish()` emits that returned unit — with a fail-closed guard (refuse/warn) when the produced unit is not metre, since the contract requires metres, not merely honest yards. This is the smallest boundary change that breaks the tag/value decoupling. Schema versioning or a migration program (T-012) would be the path only if the recipient convention ever legitimately changes — out of scope here. Secondary correction (T-014): carry source-unit, selected-profile id, and adapter build id on (or keyed to) the emitted record, placed where the information exists — publish time — so the next incident is attributable. The retained processing-duration histogram is irrelevant to this symptom; no resources/overload dimension activated.
