# ARCH_REVIEW — H11-007: attachment link issuance vs access removal

**route:** `{mode: ARCH_REVIEW, dp: DP-002, overlays: trust (security/), basis: object is an existing download path plus a proposed guard, judged against an accepted access-removal policy}`

## Decision (short answer)

**No.** Checking membership at link issuance does not complete the access-removal requirement. It closes only the *new-link* path. The *byte-delivery* path — a still-valid signed URL presented directly to storage — remains open until signature expiry, and the accepted policy explicitly requires refusal of "downloads initiated with a link obtained before removal," with no grace period. Your own test already demonstrates the violating download succeeding.

## Mechanism (S3–S4)

- **Candidate mechanism:** authorization is enforced at *capability-issuance* time, but the capability (signed URL) is bearer-grade and independent of entitlement: it remains sufficient for byte access until expiry. The enforcement point sits upstream of the trust boundary that actually releases bytes.
- **Knowledge frame:** FP-006 *Excess Privilege at Trust Boundary* / MP-005 — the outstanding URL grants privilege (byte fetch) that outlives the duty (membership); the storage boundary accepts more trust than the policy permits. A real trust boundary is present (revocable membership, untrusted client holding bearer URLs), so T-011's "validation at trust boundaries" applies at *use time*, not only at issuance.
- **GC check:** GC-012 (closed/coarse-grained trust) qualifier **fails** — this is not a closed single-user context; membership revocation across an external storage boundary is exactly a cross-privilege boundary. No GOOD CASE protection. No second mechanism (caching, propagation delay) is needed to explain the observed test result.

## Finding

**BLOCKER / MUST_FIX — the proposal, shipped alone, does not satisfy the accepted access-removal policy.**

- **Property violated:** accepted PRODUCT_INTENT (post-removal, every download refused, pre-obtained links included, no grace period).
- **Mechanism:** bearer-grade signed URL valid until expiry; storage honors it without membership consultation (FP-006).
- **Failure mode:** removed member (or anyone who captured the URL) fetches attachment bytes directly from storage after removal, for the remainder of the signature lifetime.
- **Impact:** material — silent breach of an accepted security/product contract; the app lead's completion claim would mark the requirement done while the primary violating path stays open.
- **refutation_or_invalidation:** would be overturned if (a) storage in fact enforced membership per fetch (contradicted by TEST), or (b) removal synchronously and totally invalidated outstanding signatures before returning (contradicted by CONFIG), or (c) product accepted a grace period up to URL expiry (explicitly rejected).

The issuance guard itself is correct and **keep it** — it properly closes the new-link path (TEST confirms). It is necessary, not sufficient.

## Minimum correction (S5, Q-046)

Protected property → mechanism → smallest change: **add membership enforcement at the byte-delivery boundary** — the storage fetch (or an authz layer/gateway in front of storage) must validate current record membership per request, so a valid signature becomes necessary but not sufficient. This preserves the supported URL flow for members (both constraints hold) and stays within the architecture intent's allowance for local download-path changes.

Alternatives, in order of preference:
1. **Fetch-time membership check at storage boundary** (min correction above).
2. **Invalidate outstanding URLs on removal** (rotate object address / revoke token family). Smaller blast radius in code, but it only satisfies "no grace period" if invalidation is atomic and total before the removal call returns; propagation races leave a residual window. Viable only with a test proving that totality.
3. **Proxy downloads through the app API with per-request authz.** Protects the property but reshapes the flow for all users (bandwidth/latency through the app) — wider than needed.

Validation (Q-050): the existing test scenario is the right acceptance test — after the fix, the same sequence must end in a refused byte fetch; add the mirror test that a member's in-flight URL still downloads (protects the availability constraint).

## Q-010 check — no ARCH_CONFLICT

"Existing issued URLs are part of the supported download flow" reads as *the URL mechanism is supported infrastructure* (preserved by the min correction), not as *URLs must be honored until expiry regardless of membership* — the latter would directly contradict the accepted policy. If anyone advances that reading, it becomes a real product-contract conflict → escalate to the expense product/security owners (AX-002; do not silently weaken either side). Under the correct reading, property and constraints are jointly satisfiable.

**Bottom line for the app lead:** the issuance guard is correct but only closes one of two download paths. The path that matters — replaying a pre-issued signed URL directly against storage — is unaffected by it, and the team's own test proves the violation.
