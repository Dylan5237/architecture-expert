# ARCH_REVIEW — Atlas snapshot client

`mode: ARCH_REVIEW · dp: DP-002 · overlay: runtime/stale-async`

## Verdict

The auditor's objection is rejected. Relative to the accepted product contract, the client's cache and asynchronous delivery do not display stale data, because "stale" under this contract means *a tile that does not belong to the view's selected manifest* — not *older than the latest published revision*. The stale-async mechanisms that make caches and late completions dangerous are absent by construction and pinned by tests. No defect; no change to the client is warranted; removing cache and async would protect no accepted property while degrading capability.

## S1 — Required properties (AX-001 anchoring)

From accepted PRODUCT_INTENT:

- **P1 (view-composition integrity):** every tile displayed in a view belongs to that view's selected manifest.
- **P2 (revision semantics):** a view represents the *selected published revision*, explicitly **not** the latest unpublished edits. Existing views remain bound to their revision; selecting a new revision starts a new view.

The auditor's implicit property — "a view must reflect the newest revision/edits" — is not the accepted contract; it contradicts P2. An evaluation anchored to a property the product explicitly rejected has no discriminative power (AX-001). Out of scope per the task constraints: unpublished editing, publisher storage economics. No applicable AX-003 non-negotiable is named.

## S3/S4 — Mechanism analysis under D-02 (FP-001 vs FP-012, no third FP)

The surface "persistent cache + async completions" pattern-matches both stale-async FPs. Checking mechanisms, not vocabulary:

**FP-001 (Unowned Runtime Work / stale overwrite via ownerless completion):** requires a late completion to mutate state outside its owner's context, or a mutable "latest tile" key a late write can clobber. Absent here. Completions attach a tile **only if its digest is in the view's captured manifest** (CODE), and no mutable latest-tile key exists. Cache entries are keyed by *content digest* — an immutable address — so a late write of a digest-keyed entry is byte-identical to an early one; there is no newer state to overwrite. Ownership of the completion's effect is answered by the view's captured manifest.

**FP-012 (Assumed-vs-Provided Guarantee Mismatch):** requires correctness to depend on an ordering/timing guarantee the execution model doesn't provide (e.g., "old-view downloads finish before a new revision is selected"). The design *removes* that dependency rather than assuming it: the manifest is captured before downloads are issued, and digest-membership gating makes the outcome order-independent with respect to completion arrival, revision selection, and reordering. TEST confirms exactly the perturbations this FP feeds on: late old-view deliveries after a new revision is selected, reordered completions, eviction between reads — the view remains composed only of captured-manifest tiles.

**Cache-surface GC check:** the cache is not a mutable shared-latest cache; it is an immutable, content-addressed, digest-verified-on-read store feeding read-only view composition (GC-014-adjacent shape). Eviction cannot produce wrong content — a miss re-fetches the *same addressed* tile and the publisher retains every selectable revision (CONFIG), so eviction affects cost, not composition. Persistent presence of old entries is storage of immutable content, not unowned mutable state — the GC-001 lesson (indefinite presence ≠ ownerlessness/unboundedness) applied to the cache dimension.

The auditor's "old cache entry ⇒ violated freshness" is exactly the naive false-positive this analysis rules out: an async completion is hazardous only when it can mutate state outside its owner's contract; here its effect is conditioned on captured-manifest membership.

## S2 — Evidence and drift

All current-behavior claims come from complementary origins that agree: CODE (digest-keyed cache, manifest capture, membership gate), CONFIG (finite tile set, bounded budget, eviction + re-fetch of same address, publisher retention), TEST (late/reordered/evicted scenarios pinned). Observed behavior matches accepted PRODUCT_INTENT (P1/P2) and accepted ARCHITECTURE_INTENT (immutable content-addressed revisions, view-per-revision binding).

**KNOWLEDGE_DRIFT: none.** The only conflict is the auditor's USER_ASSERTION against accepted PRODUCT_INTENT — a bare, unaccepted user assertion versus project evidence, which is ordinary S3–S5 adjudication, not a project-truth-surface conflict. I did not silently adopt the auditor's property redefinition, nor does the evidence force one.

On the auditor's proposed fix: removing cache and async delivery would not even deliver the property the auditor believes is violated — a synchronous, cacheless client bound to revision N still displays revision N after N+1 is published, because that binding *is* P2. The recommendation is property-free with respect to the accepted contract.

## Residual uncertainty (not decision-changing)

What would change this verdict: (a) evidence that the digest gate can be bypassed (a code path attaching tiles without manifest-membership check); (b) evidence that manifest capture races selection (capture not atomic with view creation); (c) an accepted product decision redefining freshness to "views must track the latest published revision." None is present; (c) would be an owner/product-authority decision, and even then the minimum correction would be view rebinding at selection — not cache removal. No further analysis changes the decision.

**Response to the auditor, in one paragraph:** under the accepted reader contract, freshness means manifest-consistency of a view, not recency across revisions. The client enforces exactly that: views capture an immutable manifest, every tile is content-addressed and digest-verified, and a completion can only attach a tile its own manifest names — so late, reordered, evicted-then-refetched, or cached-forever tiles are all indistinguishable in content from freshly downloaded ones. The claimed failure mechanism does not exist in this design; the recommended removal of cache and async is a capability regression protecting no accepted property.
