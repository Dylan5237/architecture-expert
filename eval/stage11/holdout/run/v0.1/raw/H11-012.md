## Review: disclosure export adapter (H11-012)

**route:** `{mode: CHANGE_REVIEW, dp: DP-003, overlays: [runtime/concurrency (stale async)], basis: the object is a proposed adapter delta to be judged before deployment, not a greenfield platform and not a production failure; the delta introduces a new async completion ordering, which activates the runtime/concurrency overlay.}`

### Decision summary

The adapter violates the accepted disclosure contract. It publishes an export when only the **main-text** review has completed, while attachment review jobs are still running, and it embeds **raw (unreviewed) attachment bytes** in the recipient-visible download. The test fixture proves the failure path: a recipient downloads an export whose attachment still contains personal information that has not passed the approved review.

The author's defense — parent owner and deadlines make late completion harmless — fails on inspection (Q-013): ownership and deadlines govern the **job's lifecycle** (it is owned, bounded, and fails-or-pends explicitly — that part is fine), but they say nothing about the **export's visibility rule**. The window between main-text completion and attachment completion is exactly the unreviewed-publication window, and no later byte replacement retracts what a recipient already downloaded.

Mechanism: FP-012 (assumed-vs-provided guarantee mismatch, MP-010). The adapter assumes main-text completion implies export completeness; independent async jobs provide no such cross-format ordering — which the accepted architecture intent states verbatim ("publication must not depend on an assumed completion order between formats"). FP-001 (unowned work) was checked and **excluded**: the jobs have a parent owner and deadline (D-02 discrimination).

Good-case gate: GC-016 does not rescue the adapter (no model/primitive guarantees attachment completion before exposure — the code waits only for main text, and the test shows the opposite); GC-001/GC-002 cover job ownership only, not the publication gate; GC-009/GC-010 don't apply — config explicitly states policy does not allow publishing unchecked material, so this is an ungoverned contract change, not a governed break.

Minimum correction (to this delta; no redesign needed — the old path already had the right semantics):
1. The publication check must require completion of **all included components** (main text + every attachment review job) before the download is exposed.
2. Assemble from reviewed component outputs, never raw bytes; drop the post-publication in-place byte replacement (a published export must not remain mutable to a late writer).
3. Keep the parallel start of attachment jobs (the legitimate latency win); the export simply stays pending until all reviews complete, or fails explicitly at the existing deadline — both outcomes are permitted by the accepted contract and config policy.

Rejected alternative: "drop slow formats if waiting hurts latency" — permanently dropping supported formats contradicts accepted product intent (AX-002: inconvenience cannot silently shrink the product contract). If latency vs completeness ever becomes a genuine capability conflict, that is a product-owner decision, not an adapter-author decision.
