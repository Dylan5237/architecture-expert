## Verdict

**No — the board-identity check is not sufficient to approve field installation.** The check is necessary and worth merging (it is implemented and its refuse-before-programming behavior is lab-confirmed), but qualification rests on two accepted required properties, and only one of them is even partially evidenced:

**Property A — incompatible board never runs the image.** The delta enforces this at the *installer*, before programming (TEST, CONFIRMED for the tested fixture). But "never runs" is decided at reset by the bootloader, and no bootloader-side identity/compatibility check is in evidence (the bootloader code is explicitly not included). An installer-side check does not by itself establish the property for every path that can select an image.

**Property B — interrupted installation boots old-complete or new-complete.** This is unevidenced, and the owner's claim that "two slots + the check guarantee recoverable boot in every interruption case" is an **assumed-guarantee claim**: two slots are structural; recoverability is a *rule* about how boot selection behaves under interruption. Per the accepted architecture intent, none of the three rules that would make the claim true are stated: whether boot-selection writes are atomic, how an interrupted program is recognized as incomplete, and which completed image reset selects. Structural redundancy without those declared semantics does not provide the guarantee (assumed ≠ provided). No GOOD CASE rescues this: model-provided guarantees are only compliant when the model actually provides them, and here the provider (boot-selection writer / reset handler) is absent from the packet.

**Product-contract note (AX-002):** "a service visit is not an accepted substitute for recoverable boot" is explicit in the accepted product intent. Field-access difficulty makes Property B *more* load-bearing, not less; approval cannot quietly lean on site visits as the recovery mechanism.

## What approval actually needs

1. **Merge the check** — it is tested and closes the refuse-before-programming gap; it is necessary, just not sufficient.
2. **Bootloader-side identity check evidenced** (or added) — Property A is a runtime property.
3. **Three declared rules with code pointers**: single boot-selection write authority; atomic (or marker-protected) selection update; commit-marker-based recognition of complete programming plus a stated reset-time selection rule.
4. **One power-interruption installation test** covering interruption during programming and during boot-selection update, asserting the old-approved/complete-new outcome — this is the natural validation vehicle once (3) exists, and it is currently the only untested leg of the accepted requirements.

Until those land, the owner's "guarantee in every interruption case" remains a hypothesis, and approving on it would accept the product contract silently on credit (AX-002).
