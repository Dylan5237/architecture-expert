## Decision rationale

**Required property (authoritative).** A displayed cue frame and its compiled command must reflect one completed cue revision; a revision may be replaced only at a UI transaction boundary (PRODUCT_INTENT, CONFIRMED). Out of scope per review charter: everything except the documented cue transaction and the import handoff (Q-009).

**Current behavior baseline.**
- All map mutations and both output constructions run synchronously on the UI event loop; no await/yield, nested pump, or callback inside the update function; the importer produces an immutable candidate and posts it to that loop (CODE, CONFIRMED).
- The runtime contract states the event loop neither preempts nor reenters a synchronous handler, and no other thread may access the map (CONFIG, CONFIRMED).
- Tests interleave import completion before/after edits including delayed completions; both outputs share the completed revision; access instrumentation shows map operations only on the UI loop (TEST, CONFIRMED).
- Approved scope: single-user offline editor, no concurrent external writers or publication paths (ARCHITECTURE_INTENT, CONFIRMED as intent; no project evidence contradicts it).

**Adjudication of the reviewer's claim.** The claim "global map without locks = data race" is a USER_ASSERTION (HYPOTHESIS, unverified) built from a generic mechanism. GENERIC_KNOWLEDGE explains the data-race mechanism family but never establishes that this project has a concurrent access path. Testing the mechanism against MP-010 / FP-012 (assumed guarantee ≠ model-provided guarantee):

- The correctness-relevant guarantees — non-preemptive synchronous handler segments and exclusive map access — are **model-provided** here (CONFIG contract), corroborated by CODE (no reentry point exists inside the transaction body; the project constraint forbids introducing one) and TEST (interleavings, instrumentation). This matches the GC-016 qualifier exactly ("non-preemptive event-loop segments actually provided by the model… must not be flagged"); the reviewer is pattern-matching the GC-016 *naive false-positive*.
- FP-012's failure mode (frame and command torn across two revisions) requires reentry midway through the synchronous handler or a second writer. Neither exists in the reviewed path; the constraints explicitly exclude introducing them.
- FP-001 (unowned stale overwrite, D-02 alternative attribution) also fails its precondition: the import handoff has a locatable owner (the UI loop consumes the candidate at a transaction boundary) and no completion lands outside it.
- MP-008 dimension check: write/state authority over the cue map is effectively declared — the UI event loop is the sole write authority and the sole place outputs are constructed; the conflict dimension is vacuous inside that single-threaded confine (no second writer, no replica). "Locks" are one mechanism for enforcing authority against concurrent writers, not a requirement in their absence.

**Consequences for the demanded rewrite.** Approving a separate state service plus locks on this record would add complexity with no protected property at risk (AX-004), and the demanded isolation is in a form MP-004 exempts (single-user single-process). Worse, inserting cross-thread publication into a currently single-writer path would *add* the very FP-012 surface (stale/late delivery across threads) the current design does not have, while the revision-atomicity property is already pinned by tests.

**Uncertainty / invalidation conditions for this verdict.** The NO_DEFECT is conditional on: (a) the runtime contract's non-preemption guarantee being accurate for the deployed loop; (b) the transaction body remaining free of await/yield/reentrant pumping; (c) map access remaining confined to the loop. If the editor is ported to a runtime that preempts or reenters synchronous handlers, GC-016 stops applying and the question reopens with NEEDS_EVIDENCE on the platform guarantee.

**No KNOWLEDGE_DRIFT**: observed behavior agrees with accepted PRODUCT_INTENT and ARCHITECTURE_INTENT; a bare USER_ASSERTION disagreeing with project evidence is verification work, not drift — verification done, assertion remains unconfirmed.
