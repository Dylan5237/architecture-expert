# H11-012 — Disclosure export adapter review

`route: {mode: CHANGE_REVIEW, dp: DP-003, overlays: [runtime/concurrency (stale async)], basis: "object is a proposed pre-deployment delta to an existing disclosure path; the delta introduces async completion after recipient visibility, so DP-003 with the lifecycle+concurrency overlay"}`

## Decision rationale

**Property at stake (S1).** Accepted disclosure contract: an export becomes recipient-visible **only after every included component** — main text *and* attachments — completes the approved personal-information review. Holding an export pending is allowed; dropping formats or early unreviewed publication is not. The architecture intent adds: publication must not depend on an assumed completion order between formats. The recipient-facing download contract covers attachments as well as main text.

**Evidence (S2).** The adapter (CODE) starts attachment reviews asynchronously, waits only for main-text review, assembles raw attachment bytes, and exposes the download; its publication check tests main-text completion only. The supplied TEST proves the end-to-end consequence: a recipient downloads an export whose attachment still contains an unreviewed synthetic personal address, which is scrubbed only later. HISTORY confirms the old path assembled only reviewed components — this delta moved assembly ahead of attachment completion.

**Mechanism (S3–S4).** This is **FP-012 (MP-010)**: the publication gate assumes that main-text completion suffices for whole-export completion — i.e., it depends on an inter-format completion ordering the asynchronous execution model does not provide. The TEST fixture exercises exactly the disallowed ordering. GC-016 does not rescue it: no model-provided ordering guarantee exists here — the jobs are explicitly asynchronous. D-02 discrimination: this is *not* FP-001/MP-001 — attachment jobs have a parent owner and deadline (CONFIG), the late completion does land, and nothing leaks or orphans. Ownership is present; the *predicate* is wrong.

**Why the author's cure doesn't work.** "Parent owner + deadline make late completion harmless" (USER_ASSERTION, CONTESTED): a deadline bounds wait time and assigns lifecycle adjudication (MP-001/MP-003 concerns); it is not a visibility guarantee. It does not prevent unreviewed bytes from being exposed in the window — the TEST directly refutes the claim. Late in-place byte replacement is not remediation: disclosure to an external recipient is not undone by editing the artifact afterward.

**Why this is a BLOCKER, not a governed break or preference.** Checked GC-009/010/011 (contract-break governance): no higher-priority requirement governs this break; accepted PRODUCT_INTENT explicitly forbids it. Checked GC-001/GC-002: ownership is satisfied and not the finding.

**Minimum correction (S5, to this delta).**
1. Make the publication predicate order-agnostic and complete: **no recipient visibility until every included component's review has completed** (a join over all component reviews, not a main-text check), evaluated at the common review/publication stage per accepted architecture intent.
2. Assemble only reviewed component outputs — remove the raw-bytes placeholder entirely (post-fix, the late-replacement path becomes dead code).
3. Deadline path unchanged and compliant: export remains pending or fails explicitly; publishing unchecked material stays prohibited.
4. Post-fix validation: invert the supplied fixture — assert the download is blocked while any attachment review is pending, and assert pending/failure on deadline expiry. Crash-window check: a crash between completions leaves the export pending, which the contract allows — no early-visibility window.

*Non-blocking improvement:* enforce the all-components gate in the common publication stage rather than per adapter (MP-002: adapters are the format-variation axis; publication policy is the stable decision), so future independent adapter updates cannot reintroduce this — HISTORY shows formats evolve through exactly such updates. Local fix protects the property for this delta; the systemic guard is defense in depth, not a rewrite.

**On dropping slow formats for latency.** Not accepted: it violates accepted PRODUCT_INTENT ("all supported attachment formats remain available"; dropping is explicitly disallowed). The latency concern has a compliant sanctioned path — hold pending or fail explicitly on deadline (CONFIG). Q-010: this is inconvenience, not a fundamental capability-vs-constraint conflict, so ARCH_CONFLICT is invalid. If owners ever want to trade format coverage for latency, that is a product-capability trade-off requiring an explicit contract change by product authority (AX-002) — flagged conditionally, not escalated now.

**KNOWLEDGE_DRIFT** (trigger 1 and 2: delta behavior vs accepted PRODUCT_INTENT and ARCHITECTURE_INTENT): recorded below; the correction realigns behavior with both accepted records. No intent-side change is requested or assumed.

**Bottom line:** do not deploy as-is. The adapter's "sooner availability" is the violation itself — it publishes unreviewed attachment bytes by assuming an ordering its own async jobs don't provide (FP-012). The fix is small and local: gate visibility on completion of *all* component reviews, in either completion order, and never place raw bytes into a recipient-visible artifact. Deadlines and the parent owner are real but address a different principle; they cannot cure this one.
