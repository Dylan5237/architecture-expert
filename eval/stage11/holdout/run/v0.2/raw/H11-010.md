## Decision summary

**The auditor's "necessarily stale" claim is refuted; the client has no defect.** Three independent reasons:

1. **The auditor has substituted a different product contract.** Accepted PRODUCT_INTENT defines freshness as *revision pinning*: a view represents the **selected published revision**, and every tile must belong to that view's selected manifest. It does not require "newest published revision at read time." Displaying the selected revision's tiles is the contract being honored, not a violation of it. "Old relative to a newer revision" is not "stale" under this contract.

2. **Content addressing makes cache age correctness-inert (D-02 adjudication, both FPs absent).**
   - **FP-001 (Unowned Runtime Work) — mechanism not present.** FP-001 requires ownerless work or a stale completion overwriting newer state. Here the cache is keyed by *content digest* and verified on read; nothing is ever overwritten — an "old" entry can only be a hit for a digest that the requesting view's manifest itself names, or it is not consulted at all. There is no mutable latest-tile key, so the classic stale-async-overwrite surface (late write from a superseded context landing on current state) is structurally absent. Downloads are owned by their view (finite tile set, bounded budget, effects gated by the view's own captured manifest).
   - **FP-012 (Assumed-vs-Provided Mismatch) — mechanism not present.** FP-012 requires correctness to *depend* on an ordering/cancel/timing guarantee the model does not provide. This design removed that dependency: the view captures a manifest **before** issuing downloads, and a completion attaches only if its digest is in **that captured** manifest. Any completion order, any delay, any eviction interleave yields the same invariant (view ⊆ captured manifest ∩ digest-verified bytes). TEST confirms exactly the FP-012 perturbation set — late delivery after a new revision is selected, eviction between reads, reordered completions — and the invariant holds. This is the canonical FP-012 mitigation ("remove the dependency on the guarantee"), not a violation.
   - **GC-016 qualifier check:** the naive flag here ("async + persistent cache ⇒ stale reads") is the same false-positive class GC-016 exists to block — penalizing a form because it *looks* like it relies on scheduling behavior, when the needed property is actually enforced by a real local mechanism (manifest capture + membership gate + digest verification). GC-001 was also on the route; its qualifier (lifetime ≠ ownerlessness) is not the contested surface here.

3. **The auditor's remedy doesn't deliver even the auditor's implied contract.** Removing cache and async would not make a revision-pinned view show newer data — pinning comes from view-selection semantics, not from the cache. It would add no correctness guarantee (the invariant already holds without ordering assumptions) while converting the eviction-miss path into an every-read path against the publisher. A remedy that maps to no present failure mechanism and does not produce the claimed property is not a minimum correction; it is a cost with no protected-property justification.

**Evidence authority note:** the auditor's premise is a bare USER_ASSERTION contesting accepted project evidence — per the authority matrix this is ordinary S3–S5 adjudication, **not** KNOWLEDGE_DRIFT (observed behavior *agrees* with accepted PRODUCT_INTENT; there is no project-truth-surface conflict). The claim was checked and failed.

**Conditions that would change the verdict** (invalidation of this adjudication, not open findings):
- Cache keys becoming logical-tile (non-content) keys, or removal of digest verification on read → the cache becomes a genuine stale-substitution hazard; the analysis flips.
- Publisher dropping selectable revisions → eviction-miss re-fetch could fail for bound old views; that is a publisher-side reader-contract break (and storage economics are explicitly out of scope here), not a client cache defect.
- An *authoritative* acceptance that views must auto-track the newest published revision → that is a product capability trade-off for the owner (AX-001/AX-002), a different review object (selection semantics), and even then cache removal would not be the correction.

**Bottom line for the auditor:** under this system's accepted contract, the persistent cache is content-addressed storage whose entries have no age semantics — an entry is either exactly what a view's own manifest names or it is not consulted — and async delivery is made correct by capturing the manifest before issuing downloads and gating every completion on membership in that captured manifest. "Necessarily stale" is a category error twice over: it redefines the product contract, and it assumes an ordering hazard the code structurally does not have. No change is needed.
