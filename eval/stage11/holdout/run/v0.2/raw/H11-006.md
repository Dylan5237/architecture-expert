## S3–S4 — Mechanism and GC gate

The assertion behind approval is a textbook **FP-012 / MP-010** shape: *two slots* is assumed to *provide* crash-atomic installation. Two slots provide spatial redundancy, not the three load-bearing guarantees:

1. **Selection-commit window** — power lost during/torn across the boot-selection write can leave "no valid selection" or a partially written selection;
2. **Validation-ordering window** — selection committed before the *programmed slot* (not the source file) is verified complete (the existing digest check verifies the file, not the flash contents);
3. **Recognition/fallback rule** — if the reset handler does not validate the selected slot and fall back to the other approved image, a partial slot can be selected.

Any one of these unprovided ⇒ a device that boots **neither** approved image ⇒ field brick recoverable only by site visit, which accepted intent rejects.

GC gate (S4): **GC-016 checked** — it exempts guarantees the model *actually provides*. Here the guarantee's existence is UNKNOWN (intent silent, providing code absent), not provided-and-unrestated. GC-016 does not exempt; adjudication proceeds. No KNOWLEDGE_DRIFT: no accepted intent record claims atomicity; the owner's statement is a bare USER_ASSERTION (Q-007) — verification, not drift.

## S5 — Adjudication and minimum correction

**The board-identity check is necessary but not sufficient for qualification.** It demonstrably closes the installer-path P1 breach (test-confirmed refusal before programming). It does nothing for P2, for which the packet contains zero supporting evidence in code, intent, or test.

Minimum correction to the *qualification packet* (§11: named as concrete techniques because they break the named mechanisms — contingent on the unseen code, not canonical tactics):

1. Supply the **boot-selection writer + reset handler/bootloader code** (or vendor-documented primitive semantics): is the selection commit torn-write-safe, and does reset validate a slot and fall back?
2. If gaps exist: smallest changes are (a) read-back digest verification of the inactive slot **before** any selection write; (b) a sequence/CRC-marked selection record the reset handler treats as invalid → keep old slot; (c) reset-time slot validation with fallback to the other approved image. Widen only if the existing bootloader cannot host these.
3. **Power-interruption campaign** as the discriminating test: cut power phase-aligned across programming / selection write / post-write, repeated; pass = post-reset boots old or complete new image every time.

If the bootloader already implements (b)+(c), F1 downgrades to a documentation-plus-test gap — that is exactly what the requested evidence decides.
