## Mechanism (S3–S4)

FP-006 Excess Privilege at Trust Boundary (MP-005): the signed URL is a self-contained bearer capability whose download privilege is decoupled from the membership duty. Revocation of membership does not propagate to already-minted capabilities, so the storage boundary continues to grant a privilege the duty no longer justifies.

## Findings

**F1 — BLOCKER / MUST_FIX.** Post-removal downloads remain possible via pre-issued signed URLs until expiry.
- Property: accepted access-removal policy (security; PRODUCT_INTENT).
- Mechanism: FP-006 — persistent bearer capability outliving the revocation of the duty it was granted for.
- Failure mode: removed user downloads expense-attachment bytes after removal using a link obtained while a member.
- Impact: material and demonstrated (TEST), not hypothetical; exposes attachments to removed users for the full URL lifetime.
- `refutation_or_invalidation`: overturned only if storage actually validates membership per request (it does not, per CODE/CONFIG/TEST), or if product/security owners explicitly revise the accepted policy to permit a grace period bounded by URL lifetime — which AX-002 requires as an explicit owner decision, not a silent weakening.

**F2 — NON_BLOCKING_IMPROVEMENT.** Shortening signed-URL TTL narrows the exposure window but cannot alone satisfy "no grace period"; a window of any length still violates the accepted property.

## Minimum correction (protected property → mechanism → smallest change)

The privileged action is *serving bytes*, so the authorization check must sit at the byte-serving boundary, evaluated per request against **current** membership:

1. Make the API (or an authorizing front for storage) the download enforcement point: client requests the download through it; it runs the (existing, correct) membership check per request and then serves/streams the bytes or brokers the storage read. Storage URLs are no longer handed directly to the client.
2. Keep the issuance-time guard as-is — it correctly refuses new issuance and stays useful.
3. No wider redesign is needed: this is a local change to the download path, which ARCHITECTURE_INTENT explicitly permits, and it preserves member downloads (members pass the check). Preserving client-direct storage fetchs for efficiency is an implementation convenience and cannot silently override the no-grace-period contract (AX-002).

Honest residual edge: a per-request check refuses every *new* download after removal, but a stream already in flight when removal lands may run to completion. If the policy's "every later download" is meant to include mid-stream cessation, that boundary needs an explicit owner definition (byte-level cutoff would require more machinery); it does not change the main finding.
