user_request: An external reviewer calls the editor unsafe because cue data lives in a global shared map without
  locks. Review the stated execution path before we approve a concurrency rewrite.
project_evidence:
  product_intent: 'Accepted editor behavior: a displayed cue frame and its compiled lighting command must reflect
    one completed cue revision. Imports may replace a revision only at a UI transaction boundary.'
  code: All mutations and frame/command construction execute on the UI event loop. The update function reads the
    map, replaces cue fields and constructs both outputs synchronously, with no await/yield, nested message pumping
    or callbacks inside that function. Background import code produces an immutable candidate and sends it to that
    loop; it never mutates the map.
  config: The supplied runtime contract states that this event loop does not preempt or reenter a synchronous handler.
    No other thread is permitted to access the map.
  test: Tests schedule import completion before and after edits, including delayed completions. Both outputs share
    the completed revision. Access-instrumentation checks confirm map operations occur only on the UI loop.
  architecture_intent: The approved scope is a single-user offline editor; there are no concurrent external writers
    or network publication paths in the reviewed capability.
  user_assertion: The reviewer equates a global map with a data race and demands a separate state service and locks.
constraints:
- Review only the documented cue transaction and import handoff.
- The approved transaction body cannot introduce await/yield or reentrant pumping.
