`id`: E10-002
`title`: Checkout API retries under load
`task_object`: existing checkout service path, as-is review after recurring incidents
`requested_mode`: AUTO
`user_request`: During flash sales our checkout path degrades badly. Gateway timeouts spike, then retry traffic roughly doubles request volume, and even after the origin recovers load stays high for minutes. We think we need to migrate the checkout service from our monolith to standalone microservices to fix this. Review the architecture.
`project_evidence`:
  `code`: "Client SDK retries 3x on timeout with no jitter, no backoff growth, immediate re-issue. Server has no admission control; the inbound gateway queue is unbounded (default broker config, max-length unset)."
  `config`: "Gateway: connection pool 200, queue unlimited. SDK default retry: 3 attempts, fixed 0ms delay."
  `runtime`: "Incident 2026-08-14: origin p99 4.2s at 1.8x baseline RPS; retry share of requests reached 55% at peak; queue depth grew monotonically for 6 minutes after origin recovery."
  `architecture_intent`: "ADR-0031: 'checkout remains inside the modular monolith; traffic shaping at gateway level' (accepted 2025-11)."
`constraints`:
  - backend e-commerce, modular monolith + gateway
  - flash-sale demand can exceed capacity by design of marketing
  - ADR-0031 is an accepted decision; changing it requires architecture board sign-off
`notes_for_runner`: Fresh context per case.
