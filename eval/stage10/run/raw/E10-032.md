# PR #188 Review — CI whole-suite retry gate

**route:** `{mode: CHANGE_REVIEW, dp: DP-003, overlays: [resources, overload], basis: object is a concrete delta to a running CI gate; the delta adds a retry mechanism on a shared 2-core runner, so per-work bounds and retry-amplification are the only mechanism families in play}`

**Intent & required properties (S1)**
The gate exists to produce a trustworthy signal: (P1) real regressions are caught, (P2) flake-vs-defect is attributable from outcomes, (P3) feedback latency bounded — a stated team pain point, so a real constraint, not a preference, (P4) bounded consumption of the shared runner/DB. No applicable AX-003 items (internal dev tooling, no regulatory/security constraints named).

**Evidence baseline (S2)**
- Delta behavior: on any failure, re-run entire 40-min suite once after 10 min; no per-test identification; `flaky-tests.md` untouched — CODE, CONFIRMED.
- Runner: 2 cores, shared with other teams, shared local test DB — CONFIG, CONFIRMED.
- Flakes concentrate in 6 documented order-dependent classes with reproduction notes — TEST, CONFIRMED.
- ~8% flake rate — USER_ASSERTION/RUNTIME, CONFIRMED-as-reported (number accepted; decomposition corroborated by TEST).
- Contention→flake causality (shared DB under concurrent jobs) — HYPOTHESIS (mechanism plausible, not directly measured here).
- Order-sensitive regressions can pass on a second, differently-ordered run — HYPOTHESIS (mechanism-grounded: order dependence is documented).

**Mechanisms (S3–S4), with GC gate**
The retry is bounded (count = 1) and delayed (10 min ≈ backoff). GC-015 qualifier checked: bounded retry behind an effective boundary is **not** FP-011 retry-amplification, and FP-003 unboundedness does not fire. The findings therefore do **not** rest on "retry storm". They rest on three other mechanisms the delta introduces:

1. **Masking / non-replication.** The second whole-suite run is not a controlled replication: the shared DB state and scheduling order differ (that is exactly why order-dependent tests flake). "Pass once out of two" therefore (a) masks the 6 *known, located* flaky classes instead of fixing or quarantining them, and (b) raises the gate's false-negative rate precisely for order/timing-sensitive regressions — the class this suite demonstrably contains. T-015 discipline applied: **retry ≠ idempotency** — the PR never established that re-running the suite is equivalent to running it once; for order-dependent tests over shared DB state, it is not.
2. **Attribution loss.** After this change, a red-then-green outcome cannot be distinguished from "intermittent real defect" without re-investigation; the PR also leaves `flaky-tests.md` decoupled from the gate, so the documented diagnosis surface goes unused (MP-006-shaped evidence loss for the gate's core operational question).
3. **Latency and shared-capacity cost.** Every failing run — including every genuinely broken PR during iteration — now costs 40 + 10 + 40 ≈ 90 min instead of ≤40 before red. Each failing run also schedules an extra full 40-min job on the 2-core shared runner and shared DB, i.e., retry capacity is spent exactly when the resource is likely contended (T-005 trade-off); plausibly feeding the same contention mechanism behind the flakes (HYPOTHESIS).
