## Review summary

The PR is a real improvement for the observed web double-click, but it does **not** fully address the issue it claims to fix. The property "one order per intentional submission" (accepted PRODUCT_INTENT) lives at the **shared create-order API**, and the fix lives at **one client's UI**.

**Evidence baseline**

- PR adds JS disable-on-click (CODE, CONFIRMED — that's the diff).
- Create-order endpoint: no idempotency key, no server-side duplicate window (CODE, CONFIRMED).
- Same API consumed by mobile app with its own submit logic, untouched by the PR (CODE, CONFIRMED).
- ~40 duplicate orders/month via web double-click (RUNTIME, CONFIRMED); mobile duplicate rate UNKNOWN (no guard there, not instrumented).
- "One order per intentional submission" (PRODUCT_INTENT, accepted, CONFIRMED as intent).

**Mechanism**

Duplicate-effect under re-submission with no receiver-side dedup. The button-disable relies on an *assumed* guarantee — "no second submission will ever reach the API" — that no execution model provides at the API boundary (MP-010: assumed ≠ provided; retry ≠ idempotency). It covers, at best, the two-click-event race in one web tab; it does not cover page-refresh/form resubmit, browser-level retries, or **any mobile traffic**, which uses the same unguarded endpoint.

**GOOD CASE check (S4):** GC-016 (model-provided guarantees) does not rescue the fix — the browser event loop may serialize the two click handlers, but that is a single-tab UI guarantee, not a contract at the API where two independent clients and network re-submission exist. No other GC applies.

**Minimum correction (expressible as a change to this PR)**

1. Add receiver-side duplicate-effect protection at the create-order endpoint — an optional client-generated idempotency key with a dedup store (T-015 mechanism), **and/or** a server-side dedup window keyed on (user, cart, amount, N seconds) as a *declared* conflict rule (T-013: chosen semantics, not implied). Either is sufficient; both are thin and local.
2. Keep the client-side disable as UX (fast feedback) — it is complementary, not the enforcement.
3. Optional in the same PR: log/instrument duplicate-submission hits per client so the fix is verifiable (Q-050).

This is additive and backward-compatible: no independent-consumer break (mobile adopts the key later; the dedup window covers it meanwhile), so no governed migration or cross-team escalation is required. Widening beyond this (order-pipeline redesign) is unnecessary — the local fix fully protects the property.

**Answer to your question:** No — ship it *with* the server-side patch above, or explicitly re-scope the PR to "reduces web double-click duplicates." Shipping only the client patch while calling the bug fixed would silently shrink the accepted product contract from "one order per intentional submission" to "one order per web double-click" — implementation convenience cannot redefine intent (AX-002). If the team insists that today's deadline makes even a thin server-side guard impossible, that becomes a product-owner decision (accept known duplicate orders on mobile/resubmit paths until a follow-up), not something the review can wave through.

**Out-of-scope carry-over (pre-existing, not caused by this delta):** the API's missing duplicate semantics predates the PR; the PR merely makes that gap load-bearing by claiming the fix. A full as-is pass on the order path belongs to ARCH_REVIEW if wanted.
