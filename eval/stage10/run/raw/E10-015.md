## Short answer

No — "remove all retries" targets the **trigger**, not the **mechanism**, and it does not restore the violated property.

**Attribution (CONFIRMED):** The path implements an irreversible external effect (charge creation) with no operation identity at the effect boundary: no idempotency key parameter in the API, none sent to a provider that supports them, no receiver-side dedup [CODE]. The client treats a 408/timeout as "not processed" — a guarantee no execution model here provides (MP-010 lens: assumed ≠ provided). The timeline confirms the ambiguous-outcome window: retry B was sent at 10:00:02.500, ~27.5s **before** request A's server-side timeout resolved — the client retried while the first submission's outcome was still undetermined; both created charges [RUNTIME]. So the architecture contribution is: **at-least-once submission (by design, given mobile timeouts) + non-idempotent effect + no dedup contract**. The retry is merely the duplication source that happened to fire first.

**Why removing retries fails as the correction:**

- It removes **one** duplication source. Manual resubmit, double-tap, web client, gateway redelivery all reach the same un-keyed endpoint and produce the same double charge. The property stays unprotected.
- It silently drops a real capability under a stated constraint (timeouts common on mobile → payment success rate degrades). Per AX-002, an implementation inconvenience cannot quietly shrink the product contract; that trade would need product-owner authority — and is unnecessary here, because a correction exists that protects both properties.
- FP-011's own boundary: bounded retry is not the antipattern; S-052 names *unbounded/synchronized* retry, and "does not forbid bounded retry" [T-005]. No storm signature exists in this incident (two requests, both succeeded) — FP-011 was considered and dropped as the cause.

**Minimum correction (breaks the mechanism on this path):**

1. Client generates an idempotency key **per payment intent** (e.g., derived from order ID + intent UUID created when the user initiates payment) and **reuses it across all retries of that intent** — never regenerated per attempt.
2. Backend accepts the key and forwards it to the provider (provider support is CONFIRMED in code).
3. Backend also enforces its own dedup on that key (unique constraint / idempotency record on `(order, payment_intent)`), so order-state correctness doesn't depend solely on provider behavior — receiver-side dedup is the T-015 mechanism, and the backend becomes the write authority for "at most one charge per intent."
4. On timeout, resolution is by status lookup or safe re-submission **with the same key** — ambiguity becomes harmless instead of forbidden.

Compare to wider redesign (saga/outbox/workflow engine): not required; the local contract change protects the named property. Latent risks noted out of scope: client retry policy bound/jitter unknown; the client-vs-gateway timeout mismatch (~2s vs 30s) is worth aligning but is secondary once the key exists.
