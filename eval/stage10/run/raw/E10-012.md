## Short answer

**Is the diagnosis right?** Half right. There *is* a confirmed architecture defect of exactly the class the review gestured at: an MP-006 / FP-007 violation — the evidence needed to distinguish the relevant runtime states on this path was neither captured nor derivable. But the review's causal reading is wrong in two load-bearing ways:

1. **The gap is question-relative and path-specific, not fleet-wide scarcity.** Three named unknowns on one service boundary: (a) which of the two subscription sub-flows a failing request took, (b) which upstream the routing service selected, (c) the per-request failure reason inside the routing service — plus a retention bound (1h) shorter than the recurrence interval (daily 2h window). "Add telemetry everywhere" is not the negation of this mechanism; FP-007 is explicitly *not* "missing OpenTelemetry" (checked against GC-008 / MP-006 non-prescriptions: no telemetry stack is mandated, "instrument everything" is not the principle).
2. **Part of the gap isn't a telemetry problem at all.** Upstream selection depends on an undocumented env flag. No telemetry stack, fleet-wide or not, labels the routing decision unless that decision is first made explicit. And the cheapest discriminating evidence requires **zero new instrumentation and is available today**: read the flag's current value (CONFIG), map it to the upstream via the code, then pull that upstream's own retained logs/metrics for 14:00–16:00 — nobody checked them because nobody knew which upstream to ask.

**Is the fix proportionate?** No — *as the correction for this incident* it fails the minimum-correction test on both necessity and sufficiency (AX-004 / Q-046 / Q-049):

- **Not sufficient:** with two sub-flows sharing one handler entry and no sub-flow attribute emitted, and the flag-driven upstream choice undocumented, a fleet-wide rollout reproduces the same attribution failure with nicer dashboards. The mechanism is not broken.
- **Not necessary:** the failure is confined to one merchant category on one path through one legacy service. The mechanism is breakable with a targeted change to that boundary.
- **Opportunity cost:** it spends the quarter and the budget *before* attribution, while the cheapest discriminating observations (config read, upstream-side logs, one live capture during the next predictable window) cost approximately nothing.

Fleet-wide OTel may be a legitimate *independent* platform investment — but that is a different decision object with its own required properties, and even then it would need the boundary-specific attributes this incident exposed. Decoupling it from incident closure is the recommendation.

**Hypotheses for the 502s themselves (not adjudicable in this pass — DP-005 requires competing mechanisms, not a favorite):**

- **M1** — the upstream currently selected by the flag degrades in that window (fits category-specificity + time pattern).
- **M2** — time-windowed subscription load (e.g., recurring billing batch) saturating the routing path — overload family.
- **M3** — the 2025-04 flag change routed subscriptions to an upstream whose behavior changed two weeks ago (external change, no local change).
- **M4** — a data/cohort condition only one sub-flow hits (merchants billed in that window).

These are indistinguishable *precisely because* of the FP-007 defect. Per the playbook, they are not averaged into a blocker; the discriminating observation is named below.

**Discriminating evidence (cheapest first):**

1. **Now, zero cost:** read the flag's current value from the environment (CONFIG — obtainable, not yet read), map to upstream via CODE; recover what the 2025-04 change switched (HISTORY/deploy records). Separates M3 from M1/M2/M4.
2. **Now, low cost:** pull the identified upstream's own logs/metrics for the window over the past two weeks (its retention is likely ≫1h). If the upstream shows failures in-window → M1/M3; if it shows no anomalies → M2/M4.
3. **Next window (≤1 day):** live capture at the routing service during 14:00–16:00 — existing 1h retention is sufficient if capture is live or exported on event — recording {sub-flow id, flag value, selected upstream, upstream status, latency} per request. Separates M2 (saturation signature) from M4 (sub-flow/data-specific). If the failure no longer recurs, substitute a canary/staging replay of both sub-flows under production flag values — still targeted, not fleet-wide.

## Minimum correction (breaks the FP-007 mechanism on this path)

1. **Attribution attempt for the past incident** (no code change): steps 1–2 above.
2. **Targeted evidence placement** on the routing service only: emit the per-request record above at the shared handler entry, with retention ≥ recurrence horizon (days, not 1h). Interim: a scheduled live-capture job for the known window.
3. **Make the routing decision explicit:** document the flag (name, values → upstream mapping, owner), restoring an answerable owner for that mutable routing state. Without this, step 2's "selected upstream" attribute has no authoritative semantics.
4. **Comparison to the proposed wider fix:** fleet-wide OTel to 200 services = quarter + significant budget, touches 199 services that are not on this failure path, and still does not emit sub-flow identity or routing-decision provenance → fails Q-046/Q-049 on both counts. Wider rollout is justified only by properties this pass has not been asked to establish.
