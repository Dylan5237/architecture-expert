## Decision rationale

**Protected property (S1).** 10ms hard control deadline, safety-rated — an applicable AX-003 contextual non-negotiable: no fix may relax it, and "occasionally misses" is a defect, not a tuning question. Constraints: Cortex-M / 128KB RAM, no CAN hardware change this year.

**Why "bigger CPU" is wrong (mechanism discrimination).** Control is the highest-priority preemptive task (CONFIG: control=9 > telemetry=2). Under fixed-priority preemption, lower-priority CPU demand *cannot* delay the control task — the RTOS genuinely provides that guarantee (GC-016 qualifier checked: it is real, so telemetry's CPU share is not the mechanism). Therefore a 3–18ms lateness of the highest-priority task can only come from **blocking on shared resources**, which clock speed does not reduce: mutex hold during a 200ms UART drain and allocator serialization are wall-clock-bound, not MIPS-bound. Marketing's hypothesis is dropped on mechanism, not preference.

**Attribution.** RUNTIME shows misses correlate with telemetry bursts (200ms log spikes). CODE/CONFIG show exactly the shared-resource graph those bursts travel on:

1. **Per-iteration `malloc` in the control loop** from the single shared heap arena — the deadline path contains an operation with no worst-case bound (FP-003, unbounded per-work execution time), serialized/contended with telemetry's burst allocations.
2. **Telemetry holds a global UART lock** while draining a buffer with no flow control — unbounded lock hold time (FP-003 wait dimension), an unbounded-priority-inversion exposure if any control-visible path touches that lock.
3. Structurally: the telemetry burst propagates out of its own duty into the control failure domain via shared heap + shared UART — **FP-004 Shared-Resource Failure Cascade**; blast radius (pressure oscillation) exceeds the intended failure domain.

**GOOD CASE gate (S4).** GC-004 (indefinite lifetime, bounded per-work) does not apply — the per-work time bound is precisely what is missing. GC-002 does not apply — no managed heap/soft budget exists on bare Cortex-M. GC-005 supports that no process/hardware split is required; economics favor partitions and lock discipline. Attribution at the level of "shared-resource blocking in the control path" is CONFIRMED (correlation + code structure). The split between heap-serialization vs UART-lock hold is HYPOTHESIS, but the minimum correction breaks both, so the decision does not change on it.

**Minimum correction (smallest changes that break the mechanism, in order):**

| # | Change | Mechanism broken |
|---|---|---|
| 1 | Replace control-loop `malloc` with statically allocated / pre-allocated pool packet structs (code-only) | Removes the unbounded-time allocator and the heap from the deadline path |
| 2 | Partition the heap (CONFIG: single arena → control-static + telemetry static pool); no dynamic allocation in the telemetry burst path | Removes cross-coupling and fragmentation pressure; fits 128KB (packet structs are small) |
| 3 | Control never touches the global UART lock; telemetry owns a **bounded** ring buffer with drop-oldest/overwrite policy (a bound plus governed discard of log work — not backpressure, not a rate limiter) | Bounds lock hold and log occupancy; log loss instead of deadline loss |
| 4 | If any shared mutex must remain on a control-visible path: priority-inheritance mutex with bounded hold | Bounds inversion; fallback only — do not add locks to the control path |

No priority changes needed; no CPU, no CAN change, no rewrite. **Validation (Q-050):** instrument control-task block time and replay telemetry bursts; success = zero iterations with blocking > margin against 10ms. A task-state trace at the next miss would additionally discriminate heap vs lock residual contribution — named as next evidence only if misses persist.

**Out of scope / latent (DP-005 stop discipline):** long-term fragmentation monitoring, drop counters on telemetry, WCET budget documentation for certification — listed, not toured.
