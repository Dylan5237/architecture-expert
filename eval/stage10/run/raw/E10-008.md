## S1 — Required properties (PRODUCT_INTENT, CONFIRMED)

| Property | Consequence for state architecture |
|---|---|
| Offline editing always available | Writes must commit locally, never block on network; sync is background |
| No device subordinate; no central locking server | Multi-writer (peer replicas); no coordinator adjudicates edits |
| **No data loss on any interleaving of edits** | Merge must be non-destructive — no accidental last-write-wins anywhere user content lives |
| Shared notebooks converge on all devices | Deterministic merge: same input ops ⇒ same state on every replica, independent of arrival order |

Constraints (CONFIRMED): team of 5, no sync-infrastructure budget, cloud is dumb relay + storage — **not an authority**. AX-003: no named regulatory/security non-negotiable in scope → none. AX-004: minimum sufficient complexity is the goal.

USER_ASSERTION (HYPOTHESIS): "JSON-ish document model" (exact schema unspecified), "like a wiki that never conflicts" (UX expectation).

## The load-bearing principle

MP-008: every state class must explicitly declare **write/state authority (V-003-D)** × **conflict/consistency semantics (V-010 suffixed)**. Omit either → FP-009 (undefined authority/conflict semantics → lost update / accidental LWW / divergent replicas). This is exactly the "lose text" failure the user is asking to prevent. GC-013 confirms local-first multi-writer with **declared** merge is a compliant form — single-writer is not required (D-14), and your product intent forbids it anyway.

## The design — what must be explicit

**A. Write/state authority, declared per state class**

1. **Documents/notebooks:** every device (and the cloud) holds a peer replica with equal write authority (multi-master). The cloud's authority is exactly *store and forward op batches* — it never merges, transforms, or adjudicates. The moment the cloud merges, it becomes an authority and violates your constraint.
2. **Each device's local durable store** is that device's source of truth for reads and the append point for its own edits. UI reads/writes only the local store.
3. **Op authorship is scoped:** a device appends only ops it authored (device/user ID on every op). Authority over the merged state is the declared merge function itself — nobody "wins".

**B. Conflict/consistency semantics, declared per data type (the core of "don't lose text")**

4. Consistency sense, suffixed per Q-019: **consistency (eventual convergence under commutative merge)** — replicas that have seen the same op set are byte-identical. Never bare "consistency".
5. **Note text = sequence CRDT** (T-013: commutative/associative/idempotent merge, chosen and declared). Concurrent inserts coexist deterministically. Document-level snapshot + last-write-wins is *prohibited by the no-data-loss property*, not by taste.
6. **Every JSON field type gets a named merge rule:** text → sequence CRDT; counters → merge-sum; sets → add-wins OR-set with tombstones; single-value metadata fields → history-preserving base (multi-value/log) with a deterministic *display* tiebreak (logical clock, then author ID). Nothing is discarded from history; the view picks deterministically.
7. **Deletion = tombstone, never destructive delete.** Concurrent edit+delete and delete+delete need a declared outcome; for note content, edit-wins preserves "no data loss".
8. **Determinism rule:** merge outcomes depend only on op content + causal metadata — never wall-clock time, arrival order, or device ranking. Clock/arrival-order LWW is both FP-009 ("last-write-wins by accident") and an assumed execution-model guarantee (MP-010): clock skew makes outcomes irreproducible.
9. **Causality + delivery metadata:** every op carries a locally generated UUID and a logical clock/version vector, so "concurrent" vs "happened-before" is decidable. Sync delivery is at-least-once; **apply is explicitly idempotent** (dedup by op ID). Retry ≠ idempotency — dedup is a declared mechanism, not an assumption.

**C. Storage / write path**

10. **Cloud shape (GC-014):** append-only, versioned op log per notebook; clients push op batches and pull deltas; state is derived on-device. The cloud stores blobs and history and nothing else.
11. **Local durability before acknowledgment:** edit → append op to local log (fsync) → UI ack → background push. "No data loss" must cover crashes, not just interleavings.
12. **Merge rules + op schema are a versioned compatibility contract** across independently released app versions (old clients must keep merging correctly with new ones — MP-007 flavored; breaking merge semantics is a governed migration, never a silent change).

**D. Explicitly not required (AX-004 non-prescriptions):** no locking/coordination server, no OT transform server, no messaging/streaming infrastructure, no conflict-resolution UI for text, no custom CRDT implementation if a mature library's mechanism covers it.

## Alternatives (Q-047)

- **Doc-level snapshots + timestamp LWW** — cheapest; **property-forbidden**: silently drops concurrent offline edits (the exact product contract violation).
- **OT with server-side transform** — preserves text but makes the cloud the merge authority and needs real sync infrastructure; violates both stated constraints.
- **Single-writer per note (checkout/locking)** — defines conflicts trivially but violates "no device subordinate" + offline availability.
- **Chosen: append-only op log + on-device commutative merge (GC-013 + GC-014 shapes)** — the only family that protects all four properties under the stated constraints. Which CRDT library (Automerge/Yjs-class vs. custom) and which embedded store are PERSONAL_PREFERENCE: both implement the required mechanism.

**Honest residual:** "never conflicts" is delivered as *no conflict UI and no lost text*; concurrent edits to the same sentence will interleave (both preserved, deterministic order). That is the inherent cost of coordination-free merging — preserved, not lost.

**Validation (Q-050):** property-based/fuzz tests over randomized op interleavings asserting (a) all replicas converge, (b) every applied edit's effect is present (no lost op), (c) re-delivery is a no-op. This is the cheapest evidence that "just works" holds before shipping.
