## Findings (both apply to the delta)

**F1 — BLOCKER / MUST_FIX: the plan violates the 24/7 requirement on its success path.**
Mechanism: schema DDL + rename + 9-service restart are coupled into one writer-stop window; stopping all writers is, by definition, announced downtime. Impact: ≥40 min of rejected orders even if everything goes right; realistic tail is longer (restart-ordering outage precedent). Refutation/invalidation: an explicit business decision re-accepting this downtime window (would convert to a governed waiver); or evidence that no writer stop occurs at all — the restart-coupling portion stands regardless of DDL speed.

**F2 — BLOCKER / MUST_FIX: the only rollback path loses accepted orders.**
Mechanism: single-step cutover has no intermediate reversible state, so rollback = restore from backup with 2h RPO on the orders DB; restart failure likelihood is evidenced (2 of 3 prior coordinated restarts had incidents). Impact: up to 2h of accepted orders destroyed plus extended outage — a correctness failure of the product's core record, on a path with demonstrated probability. Refutation/invalidation: a stepwise code-level rollback inside the plan (its absence is stated in plan v3), or evidence that backup restore is not the operative rollback.

## Minimum correction (a revision to this plan, not a redesign)

Protected property: continuous order acceptance + no loss of accepted orders. The fix implements **T-012 (explicit compatibility direction and migration path)**, reader direction first (V-013-A/B), using a concrete dual-column technique as the minimum mechanism:

1. **Phase 0 (evidence, cheapest discriminator):** confirm engine/version DDL semantics for nullable ADD COLUMN (lock class) and old-name VIEW viability; inventory all 9 consumers' use of `user_email`.
2. **Phase 1:** add new nullable column; deploy dual-write into writers **service-by-service** (manual deploy is fine — sequencing replaces simultaneity; old readers unaffected).
3. **Phase 2:** batched backfill, bounded batches, no long lock.
4. **Phase 3:** switch readers one service at a time via a per-service read/write config toggle — the smallest contract addition given CONFIG has no flags today.
5. **Phase 4:** once all 9 are verified on the new column, stop writing the old column; drop it later in an ordinary change with no window.

Rollback at every phase = redeploy prior version / flip the toggle — **never backup restore** (backup stays disaster recovery). No new services, platform, or rewrite: the phased plan is the smallest change that protects the property (AX-004). Fallback only if the engine truly cannot add a column without a long lock: brief queue-and-drain of writers around the metadata change — still not a 40-min stop.

**Uncertainty:** engine DDL behavior (named observation in Phase 0); per-consumer usage inventory. Neither changes the direction of the decision.
