## Decision rationale

**The failure mechanism is not the monolith.** Two overload mechanisms are confirmed on the checkout path, and a third-party migration to standalone microservices breaks neither of them:

1. **FP-010 Ungoverned Overload Growth (MP-009).** Flash-sale demand exceeds capacity *by design of marketing* (constraint), yet the path has no governed capacity boundary: the inbound gateway queue is unbounded (CODE + CONFIG: max-length unset, queue unlimited) and there is no admission/shedding/backpressure anywhere on the path (CODE). RUNTIME confirms the mechanism's signature: at 1.8× baseline RPS, queue depth grew monotonically — including for 6 minutes *after* origin recovery. MP-009's mechanism explicitly covers recovery traffic: without a boundary, the backlog itself keeps arrival > service rate even once the origin is healthy. That is exactly your "load stays high for minutes" symptom.
2. **FP-011 Retry Amplification (MP-009, per-work bound MP-003).** The client SDK retries 3× on timeout with fixed 0 ms delay, no backoff growth, no jitter, immediate re-issue (CODE + CONFIG). Retry share hit 55% of requests at peak (RUNTIME) — retries are not the bound, they are the amplifier. Note: retry count is technically bounded at 3; the defect is synchronization and zero spacing, which turns a timeout wave into a synchronized arrival wave on an already-saturated system.

**Why microservices does not fix this:** retry behavior lives in the client SDK and is indifferent to server deployment topology; and extraction does not, by itself, create an admission decision or a bounded queue — you would still have to build the exact boundary the fix below names. GC-015 explicitly blesses gateway/path-level placement, which is also what your own accepted ADR-0031 already prescribes ("traffic shaping at gateway level"). The migration would be a large, ADR-overriding change (board sign-off required) aimed at a mechanism it does not touch — AX-004 violation as over-engineering.

**GC / falsification check (S4):** The naive flag "service has no admission-control code" is the GC-015 false positive — but GC-015's qualifier requires that a gateway/path-level boundary *actually exists*. Here CONFIG/CODE show it does not, so the GC does not discharge. The RQ5-004 "naturally bounded load" exemption is inapplicable: marketing designs demand to exceed capacity. FP-011's false positive (bounded, jittered retry behind an effective boundary) also does not match.

**Drift found:** ADR-0031 (accepted 2025-11) records gateway-level traffic shaping as the accepted decision; current CONFIG/CODE/RUNTIME show no shaping exists. This is an *implementation gap against the accepted decision*, not a reason to overturn it — the minimum correction is ADR-0031-consistent.

**Minimum correction (protected property → mechanism → smallest change):**

- **Property:** checkout availability/latency under demand > capacity, and bounded recovery after origin restoration.
- **Boundary (breaks FP-010):** at the gateway, per ADR-0031's own placement — bound the inbound queue (max-length) and add an explicit admission/shedding policy for the checkout path (T-006 entry decision + T-008 rejection of excess; these are distinct mechanisms, not aliases). Rejected requests fail fast (e.g., 429/503) instead of queueing into latency collapse; optional T-009 degradation (explicit product policy) can reduce demand further.
- **Retry discipline (breaks FP-011):** SDK moves to bounded retry with exponential backoff + jitter (T-005), honoring rejection signals so shed traffic doesn't immediately re-enter.

**Condition that would widen the fix (named, not speculated):** if, after the governed boundary and retry discipline, the monolith's shared resources still starve checkout below flash-sale capacity — evidenced, not assumed — then a failure-propagation argument (MP-004) would justify revisiting extraction, with board sign-off. Nothing in the current evidence shows that.
