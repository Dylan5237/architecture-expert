## Review result

**playbook:** DP-002 · **overlay:** overload (retry storm / saturation / unbounded queue)

**intent_and_properties:**
- Checkout path availability/latency under flash-sale demand. Constraint: demand **can exceed capacity by design** (marketing), so the path must reach a governed capacity boundary and degrade gracefully — not accumulate unbounded backlog and collapse.
- Accepted architecture intent: ADR-0031 — checkout stays in the modular monolith, traffic shaping at gateway level. Changing it requires architecture-board sign-off.

**activated_dimensions:** overload only. *Not activated:* resources (retry count is already bounded at 3 → not FP-003; the unbounded queue is adjudicated as the overload boundary, D-04), reliability/cascade (no evidence of propagation beyond this single overload path), trust, state, integration, evolution.

**question_sets:** Q-INT, Q-EVD, Q-PRP, Q-OVL, Q-ALT, Q-UNK

**knowledge_drift:** present (trigger 2). Accepted ARCHITECTURE_INTENT ("traffic shaping at gateway level") vs observed CODE/CONFIG/RUNTIME (no admission control, unbounded queue, retry storm). Not an invalidation of the ADR — the accepted approach appears **unimplemented**, not wrong. Next evidence: confirm whether any shaping layer exists outside this snapshot; if not, the ADR's own approach is simply not yet built.

**gc_checked:** GC-015 (gateway/path-level overload control). **Qualifier not met** — GC-015 exempts missing *service-local* shedding, but here there is no effective governed boundary anywhere on the path (queue unlimited, no admission). This is not that false positive.

**findings:**

1. `BLOCKER / MUST_FIX` — **FP-010 Ungoverned Overload Growth** (MP-009)
   - *property:* checkout availability under expected overload
   - *mechanism:* arrival rate > service rate with no governed capacity boundary; gateway queue unbounded, no admission/shedding/backpressure/degradation on the path (pool size 200 does not cap queued work)
   - *failure_mode:* backlog absorbs excess demand; queue drains for minutes after origin recovery (observed 6 min)
   - *impact:* recurring checkout degradation/collapse in flash sales with a long tail after recovery
   - *min_correction:* bounded gateway queue (max-length) + admission/rejection (T-006/T-008) at the gateway — consistent with ADR-0031, no service rewrite
   - *refutation_or_invalidation:* a shaping layer outside the snapshot that bounds and sheds at the gateway would downgrade this finding; current CODE/CONFIG contradict that

2. `BLOCKER / MUST_FIX` — **FP-011 Retry Amplification** (MP-009)
   - *property:* same
   - *mechanism:* SDK retries 3× at fixed 0 ms with no jitter/backoff → synchronized re-issue multiplies arrivals into the overloaded origin (55 % retry share at peak)
   - *failure_mode:* timeout → immediate retry → more occupancy → more timeout (retry storm); offered load roughly doubles
   - *impact:* self-inflicted overload that keeps the origin saturated; recovery traffic with no boundary
   - *min_correction:* bounded retry with exponential backoff + jitter and a retry budget (T-005); retry only independently retry-safe failures
   - *refutation_or_invalidation:* if retry share were ≈ baseline with no synchronized waves, amplification would fail; the 55 % share and 0 ms config refute that

   *D-04 note:* retry count is already bounded (3), so this is **not** FP-003 (unbounded retry). The defect is synchronized, un-jittered re-issue, not an unbounded retry count. T-015 (idempotency) is complementary, not a substitute for either fix.

**Minimum correction (both required; neither needs a rewrite):**
1. Gateway: bounded queue + admission/shedding (T-006/T-008) — this alone stops the 6-minute post-recovery backlog.
2. SDK: jittered, exponential-backoff retries with a budget (T-005) — this alone stops the retry storm.

They are complementary: admission alone still admits retry storms as new arrivals; bounded retry alone still lets genuine demand > capacity queue unboundedly.

**Rejected alternative:** the proposed microservices migration does **not** break FP-010 or FP-011 — retries would still amplify, and without a governed boundary the extracted services would still overload (with added network hops). Per Q-049, a rewrite is preferred here, not necessary. It also conflicts with accepted ADR-0031.

**arch_conflict:** none — required property, constraint, and ADR-0031 are all compatible with the minimum correction. (Owner preference for microservices vs an accepted ADR is not a capability-vs-constraint conflict.)

**terminal_outcome:** MIN_SAFE_FIX_IDENTIFIED
**stop_reason:** 2 — supported material defects with a clear minimum correction

**escalation:**
- For the fix itself: **none** (routine mechanism selection with sufficient evidence).
- Conditional: if the owner insists on moving checkout out of the monolith, that changes accepted ADR-0031 → **architecture board sign-off**. Not required to fix the incidents.

---

**Bottom line:** Don't migrate to microservices. The observed incidents are fully explained by two overload-path defects — no governed boundary at the gateway (unbounded queue, no admission) and synchronized no-jitter retries — and both are fixable with configuration-level changes (gateway queue cap + admission/shedding; SDK backoff/jitter) that are *consistent with* your accepted ADR-0031 rather than a departure from it.
