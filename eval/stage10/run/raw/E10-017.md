**Mechanism (S3–S4).** FP-006 *Excess Privilege at Trust Boundary* under MP-005. An agent-action boundary is present (model-decided tool execution), which is exactly MP-005's Applies When. Granted privilege determines the action set available after mistake or misuse: TEAM-ADMIN's action set (all-environment write + user management) far exceeds the duty (trigger deployments). The human click-through is an *approval* of model-chosen actions, not a *bound* on the possible action set — it cannot remove excess privilege; and with no per-action authorization check, any approved-by-mistake or prompt-injected invocation executes with full admin authority.

**GOOD CASE gate.** GC-012 (closed/coarse-grained trust) is the only candidate escape, and its qualifier excludes this case: it requires the *absence* of relevant untrusted-input / cross-privilege / agent-action boundaries. An agent-action boundary is present. Same-team context does not rescue it — the multi-privilege (admin vs deploy-trigger) and cross-environment boundaries are the relevant ones. Finding stands.

**Adjudication (S5).** This is a BLOCKER **on the delta**. Notably, the "two sprints for per-agent identity" framing is a false dilemma: full identity work is *not* the minimum correction. A scoped credential + action allowlist breaks the mechanism without identity infrastructure, so there is no real capability-vs-constraint conflict here — the cost constraint does not force the product-scope violation (AX-002: inconvenience cannot silently expand the contract beyond accepted scope). No ARCH_CONFLICT record.

**KNOWLEDGE_DRIFT.** Accepted PRODUCT_INTENT (deployments only) disagrees with the delta's granted authority surface (user management reachable). Per DP-003, emitted below; next action is to scope the credential inside this PR, or — if broader authority is genuinely wanted — an explicit product decision by the spec owner, not silent expansion via credential choice.
