## Findings

### F1 — BLOCKER / MUST_FIX — undeclared, unbounded consistency (replica/cache) between search path and catalog

- **Evidence**
  - Catalog write authority = primary DB; poller refreshes search index from `last_updated` at 600s interval — `CODE` + `CONFIG`, CONFIRMED.
  - Redis cache in front of search, TTL 60s — `CODE`, CONFIRMED.
  - No CDC; no explicit consistency declaration anywhere — `CODE`, CONFIRMED (absence noted).
  - Measured lag p50 11min, p99 14.5min — `RUNTIME`, CONFIRMED.
  - Required property: customers must not buy unavailable items — `PRODUCT_INTENT` (accepted, PRD Sec. 4), CONFIRMED.
- **Mechanism (FP-009 → MP-008):** the search index + Redis form a derived read model of catalog state. The catalog's write/state authority (V-003-D) is the primary DB, but the replica/cache layer has **no declared** `consistency (replica)` / `consistency (cache)` semantics relative to that source of truth and no declared staleness bound. The poller interval (600s) plus cache TTL (60s) make the lag dominated by the poller. A purchase decision served from this path uses stale availability.
- **Failure mode / impact:** customer sees item as available, buys; catalog says unavailable → oversell/out-of-stock purchase. Directly violates the accepted product property.
- **GC check:** GC-013 (CRDT/local-first multi-writer) — no declared merge semantics, not applicable. GC-014 (append-only log / read-only derived view) — the index is a derived read model but no append/derive semantics are declared and no staleness contract exists, not applicable. GC-016 (model-provided guarantees) — no guarantee claimed by a model here, not applicable. `gc_checked: GC-013, GC-014, GC-016`.
- **`refutation_or_invalidation`:** the search team's counterclaim "eventual consistency, industry standard" fails three ways. (1) Lexical: unqualified "consistency" has no meaning without a V-010 suffix, and "eventual" is not a bound — it is precisely the undeclared class FP-009 targets. (2) The property is absolute ("must **not** buy unavailable"); no finite-lag eventual scheme can protect it without a purchase-time guard, and no guard is in evidence. (3) The team cannot name the bound — `USER_ASSERTION`, HYPOTHESIS, unverified.

## Minimum correction (AX-004)

The smallest change that breaks the failure mechanism is **two parts**:

1. **Declare the semantics** (T-013): catalog primary DB is authoritative (V-003-D); search index + Redis are an eventually-consistent derived read model with a *named* staleness bound for the browsing path. "Eventually consistent" stops being an assertion and becomes a contract.
2. **Protect the absolute property at the purchase path:** re-validate availability against the source of truth (primary catalog) at purchase/checkout time. The purchase decision then no longer depends on the stale derived model, which no poller interval alone can guarantee.

**Alternatives considered, not recommended as the primary fix:** restoring the 30s poller interval or adding CDC reduces the window but cannot satisfy "must not buy unavailable" — any finite lag still permits an out-of-stock purchase. Those are legitimate freshness improvements for the *browsing* path, not substitutes for the purchase-time guard. (Purchase-time re-validation is named here as a concrete technique, not a canonical T-* node.)
