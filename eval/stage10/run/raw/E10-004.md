# Architecture Review — Search Staleness (E10-004)

`route: {mode: ARCH_REVIEW, dp: DP-002, overlays: [state-data], basis: "Object is an existing search subsystem judged as-is; the deciding mechanism family is undeclared consistency semantics between the catalog write authority and a cached derived view — not overload, failure propagation, or a proposed change."}`

## Direct answer

Yes, there is an architecture defect — but it is not "eventual consistency exists," and the search team is neither simply right nor simply wrong. Two things must be separated:

1. **Eventual consistency (V-010: bounded-staleness sense) between catalog and search is a legitimate, declarable choice.** A polled derived view is even a GOOD CASE *shape* (GC-014: read-only derived view) — **provided the derivation semantics are explicit**. Here they are not: no declaration anywhere, and the team defending it "cannot name the bound." An unnamed, undeclared bound is not eventual consistency; it is **undefined consistency semantics (FP-009 / MP-008)**. That is the defect.
2. **The effective bound that exists in fact is ~10–15 minutes (RUNTIME: p50 11min, p99 14.5min), on a path that feeds a product contract (PRD §4: customers must not buy unavailable items).** The cache TTL of 60s is a bound *relative to the index*, not to the catalog — it is doing almost none of the work the team thinks it is.

Note what already happened because the semantics were undeclared: in June a cost optimization moved the poller 30s → 600s, silently redefining the system's effective staleness contract ~20×, with no declared contract to check the change against. That is the failure mode of undeclared semantics operating in the wild, and it is why the two teams are now deadlocked — there is no adjudicable rule to appeal to.

**The one fact that decides severity is missing:** whether the order/checkout path re-validates stock against the catalog authority at order time.

- If checkout re-validates → PRD §4 is protected at the order boundary; search staleness degrades to a UX/quality matter, and the remaining work is declaring an acceptable bound `B`.
- If checkout trusts the stale path (or reads via the same index/cache) → the accepted product contract is violated in fact, and the fix belongs on the order boundary, not in a search re-architecture.

The "customers buy out-of-stock items" report is currently USER_ASSERTION (no runtime order-failure evidence supplied), so I do not promote it to a proven requirement violation.

## Minimum-correction comparison (Q-046/Q-049)

| Option | Mechanism it breaks | Property protected | Cost/scope |
|---|---|---|---|
| **Declare the V-010 contract + bound B + lag test** (T-013) | Makes future silent redefinitions (June-style) checkable | P2 → enables P1 protection | Doc/ADR + one alert; smallest |
| **Revert poller 30s** (config) | Shrinks bound ~20× | Partial P1; fixes the June regression only | Trivial, reversible; does not fix F1 |
| **Order-boundary stock re-validation** | Breaks stale-data→purchase path at the property's actual boundary | P1 directly | Small, local; required if checkout trusts stale data |
| CDC / event-driven index | Replaces poll-delay with push-delay (seconds) | Fresh display, if *that* is required | Wider redesign; **not** the minimum correction for PRD §4 |

Wider redesign is justified only if product requires fresh *search display* as a capability — that is the owner trade-off named above, not an architecture finding. Nothing here prescribes a queue, a platform, or a rewrite.
