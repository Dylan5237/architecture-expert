## Review: nightly reporting global lock

**route:** `{mode: ARCH_REVIEW, dp: DP-002, overlays: [resources, reliability], basis: object is an existing reporting subsystem judged as-is; symptom family is an unbounded shared-resource hold (resources), and the team's proposal adds a structural partition/failure domain (reliability)}`

### Decision summary

The nightly report holds a global table lock across phases that have no data-consistency role (PDF render, SMTP dispatch), and the online order-read path consults that same lock. Lock hold time is therefore driven by external, variable-latency phases with no effective bound — 3 hours of occupancy on a resource the OLTP read path needs. This directly and materially violates the accepted `<2s` online order-lookup contract, every nightly window. The proposed separate-region replica does not break this mechanism: the load-bearing defect is lock **scope and hold composition**, not data locality — and runtime evidence shows the hold is *not* dominated by aggregation. The minimum correction is local: decouple the online read path from the report lock and scope/bound whatever lock the aggregation actually needs.

### Findings

**F1 — BLOCKER / MUST_FIX** (property: online order lookup < 2s)
- **mechanism:** FP-003 (unbounded per-work dimension, time/hold): per-work lock hold has no effective bound and includes non-data phases; L=λW — report work retains the shared resource ~3h, so any online read arriving in-window waits behind it. External-dependency latency (SMTP, rendering) converts directly into OLTP read latency via the shared lock.
- **failure_mode / impact:** online reads block 40–90s nightly — 20–45× the accepted bound, recurring, guaranteed by structure.
- **min_correction:** (1) Remove the online read path's dependency on the report lock — the "consistency check" consulting it is the coupling that turns report occupancy into read latency. If reports are read-only over order data (aggregation/render/dispatch involve no report writes to order state), DBMS consistent-read/snapshot semantics already give each path a consistent view; claim only what the concrete DB engine actually provides (GC-016 check). (2) Scope any remaining lock to the aggregation phase only, with a deadline (T-003); render + SMTP dispatch run after release, as bounded async side-effect phases (T-005 for dispatch retries). (3) Name the V-010 consistency sense the report actually requires — currently unqualified, so the lock's necessity is unestablished; the burden is on that claim, not on the readers.
- **refutation_or_invalidation:** a documented owner decision re-scoping the latency contract to exclude nightly windows; or tracing showing online blocking is caused by something other than the lock; or established evidence that a governing consistency requirement genuinely needs cross-path mutual exclusion that a DB snapshot cannot provide (would change the fix shape, not the property violation).

**F2 — HIGH_CONFIDENCE_RISK** (on the proposal as the fix)
- **mechanism:** mechanism mismatch + MP-004 cost model: the replica addresses data locality, but the hold is dominated by render/SMTP, so the unbounded-hold mechanism survives on whatever resource the orchestrator still locks. Relieving the symptom via the replica still requires touching the online path's lock check — which is exactly the local change in F1, done anyway. Meanwhile it adds significant cost and a new failure domain (replication lag/break), per the stated constraints and GC-005/Q-032 (structural separation not a default).
- **refutation_or_invalidation:** evidence that aggregation alone — with the lock decoupled/scoped — still degrades OLTP reads beyond 2s through DB-level contention. That would make offloading report reads to a separate store the minimum mechanism for the property. If a replica is pursued for *other* reasons (DR, report query load), that is a separate owner decision not established by this evidence (OWNER_TRADE_OFF territory, escalation list: material cost).

### Validation (Q-050)

RUNTIME, next nightly windows: p99/max online read latency < 2s; per-phase lock-hold duration (aggregation-only scope) confirming residual interference fits the read budget. Per-phase hold timing is also the standing evidence that keeps this attributable (MP-006); the existing runtime decomposition suggests it is cheaply obtainable.
