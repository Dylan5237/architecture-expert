CODE and RUNTIME agree on every sub-question; no cross-origin conflict on current behavior. Two conflicts exist against **accepted** PRODUCT_INTENT → recorded as KNOWLEDGE_DRIFT (below); mechanism attribution needs no further evidence.

### Mechanism

The freeze is **thread affinity of the work, not the database**. The WPF-style execution model provides exactly one UI message-pump consumer; a handler that runs a whole-album SELECT plus per-file encode/write occupies it for the full duration. "The UI stays responsive during a long handler" is an *assumed* guarantee the model does not provide (MP-010 framing); the per-work time dimension on the app's most contended resource is unbounded (FP-003 / MP-003). GC-016 does **not** exempt this — the model genuinely withholds that guarantee. The data loss is a separate durability gap: edits live only in memory, and forced kill performs no cleanup (T-002), so the freeze *widens the exposure window* and makes the kill likely.

GC qualification before findings: GC-005 (single-process SQLite is compliant — process boundary not required by this cost model), GC-004 (process lifetime is not the issue; per-work bounds are), GC-002 (heap growth is semantic occupancy, not a missing collector). None exempts the two defects; GC-005 does exempt the architecture's single-process shape itself.

### Verdict on the proposal: **No — do not move SQLite writes to a background service process**

1. **It misdiagnoses the mechanism.** Evidence attributes the freeze to *all* export work on the UI thread (query + encode + writes). Relocating only DB writes leaves encode and reads blocking the pump; the freeze persists.
2. **It is not deployable within stated constraints** ("no background services on user machines beyond the app itself").
3. **It fails AX-004 / GC-005 / MP-004 non-prescription**: a second process adds IPC, deployment, lifecycle ownership (who starts/stops/upgrades it — MP-001), and re-opens SQLite write/state authority across a boundary (MP-008: the DB file would have two potential writers; authority must be re-declared) — to solve a problem that is intra-process scheduling.
4. **It does not touch the second property.** Edits lost on force-kill need durable write-through, which a service process neither requires nor provides.

### Minimum corrections

1. **Move export off the UI thread, within the process** (T-001/T-002 as concrete techniques): background worker owned by the `ExportViewModel` scope, cooperative `CancellationToken`, progress and the observable-collection update marshaled back via the dispatcher. Page the album query and stream JPEG writes in bounded chunks (T-003/T-004 shaping) so per-work time and memory stop scaling with album size.
2. **Durable write-through of edits to SQLite on the edit path** (bounded interval acceptable). Single writer stays the app process — no authority change. After this, a kill can only lose in-flight export artifacts, never edits.
3. **Validation (Q-050):** a test asserting UI-thread message pumping during export + cancellation mid-export; a kill-during-export durability test. The current test cannot detect either defect.
