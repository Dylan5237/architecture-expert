## Decision in brief

**No — do not move SQLite writes to a background service process.** That proposal is wider than the failure mechanisms require and does not protect the required properties. The minimum correction is two in-process changes plus one bound:

1. Run the export unit off the UI thread (in-process background worker with cancellation) — fixes the freeze.
2. Persist edits incrementally to SQLite so the durable store is the write authority — fixes the force-kill loss.
3. Stream/page the export in bounded batches — removes the album-sized memory growth.

The first two are violations of **accepted** product contract, not style concerns.

## Findings

### F1 — UI thread blocking (BLOCKER / MUST_FIX)
- **property**: "Export must not block the UI" (PRODUCT_INTENT).
- **mechanism**: FP-003 event-loop blocking (S-088) — synchronous, unbounded-per-work-time I/O (SELECT + JPEG + collection update) consumes the single UI thread.
- **failure_mode**: message pump starved 10–40s → "Not Responding" → user force-kill.
- **impact**: direct violation of accepted product contract; provokes F2's data loss.
- **min_correction**: move the whole export unit to an owned in-process background worker (structured lifecycle T-001, cancellation T-002); marshal progress/completion back to the UI thread. **Not** a separate process.
- **refutation_or_invalidation**: CODE showing an existing off-thread path, or a RUNTIME trace with the UI thread idle during export, would overturn. Neither exists; CODE and RUNTIME agree.

### F2 — Volatile write authority for edits (BLOCKER / MUST_FIX)
- **property**: "user edits are never lost on force-kill" (PRODUCT_INTENT).
- **mechanism**: write/state authority (V-003-D, MP-008) for user edits sits in volatile in-memory state; SQLite is a lagging snapshot written only at export.
- **failure_mode**: force-kill (provoked by F1, but also any crash/power loss) destroys the authoritative edit copy.
- **impact**: direct violation of accepted product contract (data loss).
- **min_correction**: make SQLite the write authority for edits and persist incrementally (write-through per edit, or a durable WAL/journal); the in-memory collection becomes a read model.
- **refutation_or_invalidation**: durable persistence at/before edit time (autosave/journal) or a recovery path re-applying edits after kill would overturn. CODE shows none.

### F3 — Unbounded per-work memory (HIGH_CONFIDENCE_RISK)
- **property**: bounded per-work memory (MP-003); supports both required properties under large albums.
- **mechanism**: FP-003 — whole-album SELECT materializes the album; JPEG buffers scale with album size (RUNTIME: heap grows with album size).
- **failure_mode**: large album → memory pressure → OOM/crash → data loss (amplifies F2).
- **impact**: material risk to availability and to the edit-durability property.
- **min_correction**: stream/page the export in bounded batches (page the SELECT; process photos in bounded batches); add a deadline (T-003) and bounded occupancy (T-004).
- **refutation_or_invalidation**: an enforced album-size cap (input-limited batch as an implied bound, GC-004) would downgrade this; no cap is in evidence.

## Assessment of the proposed fix ("move SQLite writes to a background service process")

- It does **not** cleanly break the F1 mechanism: the blocking work is the *export unit itself* (SELECT + JPEG I/O), not SQLite writes alone. Unless the whole unit leaves the UI thread, the freeze remains; leaving it is achievable in-process with a background worker.
- It does **not** fix F2: a separate process does not persist the in-memory edits; it adds queueing and a second failure point *between* edits and durable storage.
- It **adds** complexity without a property gain (AX-004): an IPC boundary, serialization, a second process lifecycle to own (MP-001/FP-001), and a second SQLite writer whose conflict rule must be declared (MP-008/Q-STA). SQLite single-process is a compliant form (GC-005/S-117), and the Constitution does not prescribe process boundaries (usage contract #7). With a team of 4, no ops, and no allowed background services, a second process is a lifecycle liability, not a fix.
- Correct framing is **off-thread execution**, not **off-process storage**.

## Minimum correction (order matters)

1. **Off-thread export** (breaks F1): in-process background worker + cancellation + UI marshaling. Add a test asserting the export does not run on the UI thread and honors cancellation (the current 50-photo test cannot detect F1).
2. **Incremental edit persistence** (breaks F2): SQLite as write authority; write-through/journal per edit. Add a test asserting force-kill loses nothing.
3. **Bounded-batch export** (breaks F3): page the SELECT, bounded photo batches. Add a test asserting peak memory is independent of album size.

Items 1 and 2 are independent properties; neither alone satisfies both requirements. The wider rewrite (a service process) is rejected because the local fixes protect the properties (Q-046/Q-049).
