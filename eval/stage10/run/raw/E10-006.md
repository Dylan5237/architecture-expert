## Second opinion — verdict

**The architect's memo commits a category error, and the system as evidenced is compliant.** The inference "long-running processes with indefinite lifetime ⇒ unbounded resource usage" conflates two dimensions that MP-003 (Bounded Execution) explicitly separates: **lifetime of a service/stream may legitimately be indefinite; what must be bounded or governed are the per-work dimensions.** "Runs forever ⇒ unbounded" is the exact naive false-positive registered as GC-004, and "supervised daemon = missing ownership" is the exact naive false-positive registered as GC-001.

Checking the actual per-work dimensions against project evidence (not the memo's vocabulary):

| MP-003 dimension | Project evidence | Verdict |
|---|---|---|
| Per-order execution/wait time | 5s timeout guard per order (CODE) | Bounded |
| Restart amplification | `one_for_one`, `max_restarts 3 in 5s` (CONFIG) — crash-looping terminates in supervisor escalation, not infinite churn | Governed policy |
| Queue / memory occupancy | Selective-receive mailbox; 7 months stable memory, no leak trend, p99 12ms (RUNTIME) | No FP-003 signature observed |
| Ownership | Supervisor owns create/restart/stop per stream; matches accepted design doc "supervision owns restart" | Explicit ownership (GC-001) |

The failure mechanism the memo implies (FP-003: unbounded per-work dimension exhausting shared capacity) is **not present**: its observable signature — growing queues, memory trend, latency collapse — is contradicted by 7 months of stable RUNTIME evidence, and each candidate dimension already has a bound or a governed policy. Per AX-001, there is also no required property that a rewrite would protect which is currently unprotected.

**On the proposed remedy ("bounded lifecycles + per-process expiry"):** it would not bound anything that is currently unbounded, and it would *replace* failure-driven, supervision-owned restart with time-driven expiry of healthy streams. For a 24/7 order router whose per-stream `gen_server` holds session state, arbitrary expiry forces new state-handoff / re-subscription machinery — a new correctness burden and a self-inflicted availability risk — with no property demanding it (AX-004: minimum sufficient complexity). **Recommendation: do not schedule the rewrite on this basis.**

**What would change this verdict** (named discriminating evidence): a per-node time series of process count and max mailbox length, ideally across a burst window. Evidence of unbounded dynamic process spawning or burst-driven mailbox growth invisible in aggregate memory would re-open FP-003 — and even then the minimum correction would be a bound or policy at that dimension, not a lifecycle rewrite.

**Knowledge drift:** none. The memo is an unverified USER_ASSERTION against project evidence (ordinary adjudication, not a drift trigger); the accepted design doc *agrees* with observed behavior.
