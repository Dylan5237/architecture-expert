## What actually failed

**Capacity arithmetic, not the worker pool.** Measured: 30k/s insert demand at peak vs 8k/s DB insert ceiling. Worker CPU 100% is a symptom — workers are insert-bound; scaling 50→500 workers cannot change an 8k/s DB ceiling. L=λW: arrival > service with no boundary → unbounded backlog → latency grows without limit (2s → 4h). This is exactly the incident's shape.

**Attribution — three mechanisms, one dropped on evidence, one adjudicated real:**

1. **FP-003 Unbounded Per-Work Dimension (fan-out)** — CONFIRMED. One work item (one post) materializes 2.1M notification insert jobs. The fan-out dimension per work item has no effective bound (CODE: fan-out-on-write, one row per follower).
2. **FP-010 Ungoverned Overload Growth** — CONFIRMED. The path meets *no* governed capacity boundary anywhere: unbounded Kafka topic growth, fixed consumers, no admission or shedding on the notification API (CODE + CONFIG). Viral spikes are the product working as intended (PRODUCT_INTENT constraint), so demand legitimately exceeds capacity and MP-009 applies — the "naturally bounded load" exemption does not.
3. **FP-011 Retry Amplification** — dropped. The backlog is fully accounted for by first-offer fan-out; no retry storm, synchronized retry waves, or retry-dominated traffic appears in the RUNTIME record.
4. **FP-004 Shared-Resource Failure Cascade** — real, and it is why the incident is an *SLA breach* and not a social-feature annoyance: a single notification class, single queue, and single DB insert ceiling means a social-post failure domain's blast radius crosses into direct-message notifications. FP-005 does not apply (no coupled defense existed to amplify).

**GOOD CASE check (S4):** GC-015 does not rescue the system — it excuses *placement* (path-level rather than service-local control), not *absence* of any boundary; here no boundary exists at any placement. GC-004 does not apply — the queue is a per-work dimension, not service lifetime. No legal form is being blamed.

## Proportionate fix (minimum correction)

Protected properties: (a) DM notification latency (contractual SLA — non-negotiable); (b) notification service availability under intended viral load.

1. **Split the failure domain first (T-010): separate topic + consumer pool + reserved DB capacity for DM notifications.** Smallest change that breaks the FP-004 propagation edge and restores the contractual property immediately — even while the social path saturates. DM volume is small; cost is trivial.
2. **Bound the fan-out dimension at admission (T-004 + T-006): cap materialized fan-out per post** (e.g., posts above a follower threshold get bounded/delayed/batched materialization). This breaks FP-003 at its source — the 2.1M-job enqueue is what exceeds capacity; workers were never the ceiling.
3. **Governed degradation for the viral class (T-009): fan-out-on-read or digest for high-follower posts.** This is legal degradation of a *non-contractual* property (social notification immediacy), not a silent contract shrink. Which degradation form (drop / batch / read-time) is a product capability trade — it must be ratified by the product owner (AX-002), not chosen silently by the implementer.
4. **Do not** scale workers, shard Kafka, or re-platform notifications: none addresses the 8k/s DB ceiling, and DM isolation + admission bound already protect both properties (AX-004).

**Comparison to redesign:** a notification-service rewrite (per-class services, new storage) buys nothing the local fix lacks; it only adds migration risk.

## Remaining uncertainty

- Whether the 8k/s insert ceiling is structural (storage engine, indexes) or cheaply tunable — changes the *capacity headroom*, not the need for a boundary. Named next observation: insert-throughput profile under load. Not decision-changing for the fix above.
