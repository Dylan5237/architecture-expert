## What went wrong, architecturally

**Broken property (S1):** the accepted constraint *"workers must not outlive their run"*, under the stated condition *"coordinator restart is routine."* A coordinator crash is an in-envelope event this pipeline is required to survive with contained consequences. It did not.

**Mechanism (FP-001 — Unowned Runtime Work, MP-001):** the coordinator spawns JVM workers fire-and-forget. Nothing in the runtime ties worker lifetime to run scope: no cancellation token is passed, no shutdown hook exists, workers do not monitor coordinator liveness (CODE, CONFIRMED). When the coordinator was OOM-killed at 03:14 (RUNTIME, CONFIRMED), ownership of those 47 workers became vacant — no process could answer "who stops these." They continued staggering through batches against the old mapping, writing to both schema variants, some after the new consumer started at 03:20, until a human became the adjudicator at 06:05 (RUNTIME, CONFIRMED). That is the defining signature of FP-001: after owner death, cleanup/cancellation is *unassigned*, so work outlives its context.

Note the distinction: the coordinator crash is the failure event; the orphaned writes are the **blast radius** — which extended across the migration boundary (legacy + new topic schemas) and past the cutover point. The schema mixing is a consequence, not a second initiating mechanism.

**Competing mechanisms considered and dropped (D-02 gate, S3/S4):**

- **FP-012 / MP-010 (assumed execution-model guarantee):** would apply if the design *relied* on a guarantee the platform doesn't provide — e.g., believing Linux/JVM kills children when the parent dies (it doesn't, absent PDEATHSIG/process-group action). The CODE evidence shows no mechanism *and* no recorded reliance on one; the simplest attribution is absent ownership, not a false guarantee. Discriminating evidence if anyone disputes this: any ADR/comment/config asserting parent-death cleanup. If found, add the FP-012 lens — the correction below barely changes.
- **FP-003 / MP-003 (unbounded execution):** workers did run ~2h45m unbounded, but the violated property is lifetime scoping, not a missing numeric bound. A time limit would have *masked* the ownership gap. Secondary, not attribution.
- **FP-008 / MP-007 (contract break):** post-cutover legacy writes are real, but they are the blast radius of the orphan mechanism. Data reconciliation is a follow-on task, not this attribution.

**GOOD CASE check (S4):** GC-001 does not shield this — indefinite worker lifetime is legal *under supervision*; here there is no supervisor at all. GC-002 is irrelevant (JVM heap reclamation ≠ semantic ownership). GC-016 would apply only if the runtime actually provided child-death-on-parent-exit; observation proves it does not. No GC qualifier matches.

**Recurrence:** HISTORY (CONFIRMED) shows the same signature in March, misattributed to "bad batch data." This is not a novel failure; the mechanism was latent and misread once already.

## Smallest safe correction

Protect the property "workers must not outlive their run" by breaking the orphan mechanism at its cheapest points — no orchestrator rewrite, no job-framework migration:

1. **Make the run the owner, survivably.** Workers monitor coordinator liveness between batches (heartbeat/lease with TTL, or an OS primitive such as parent-death signal on the worker processes) and **self-terminate at batch boundaries** — the natural yield point, which also avoids creating new mid-batch partial writes. This is T-002 cancellation propagation placed where cooperative cancel is cheap.
2. **Make the coordinator's exit own its children.** Spawn workers in a dedicated process group; coordinator exit/restart kills the group (T-001 supervised lifecycle, minimal form).
3. **Reconcile on startup.** Stamp workers with a run ID; a restarting coordinator kills or refuses any worker carrying a stale run ID. This closes the already-orphaned case that (2) alone misses when the parent is OOM-killed.

Wider redesign comparison: a workflow engine or queue-based worker pool would also fix it, but none of its additional capability is required by the named property — the three changes above restore ownership and cancellation for this path at a fraction of the change risk (AX-004, minimum-correction rule).

**Supplementary (NON_BLOCKING_IMPROVEMENT):** a hard per-work wall-clock bound on each worker as belt-behind-the-suspenders if the liveness check itself fails.

**Out-of-scope follow-ons (listed, not toured here):** (a) reconcile the 03:20–06:05 legacy-topic writes against what the new consumer processed — that is its own DP-003/DP-002 pass, and if it requires irreversible data repair it escalates there; (b) amend the March incident record.
