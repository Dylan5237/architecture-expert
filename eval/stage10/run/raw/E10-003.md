## What went wrong, architecturally

The incident is **FP-001 — Unowned Runtime Work**, not a data-batch problem and not a contract break.

- **Property that broke:** "workers must not outlive their run" (stated constraint), plus the correctness of the migration cutover (no stale writes after the new consumer takes over).
- **Mechanism:** The coordinator spawned 47 workers with no supervisor, no cancellation token, no shutdown hook, and no coordinator-liveness monitoring (CODE, CONFIRMED). When the coordinator was OOM-killed at 03:14 (RUNTIME, CONFIRMED), no actor owned *stop/cleanup* for the workers. They kept mutating state — FP-001's amplification path "orphaned workers keep mutating" — writing to legacy and new topics for ~2h45m until a human killed them at 06:05 (RUNTIME, CONFIRMED).
- **Why the dual-schema write is a consequence, not a second defect:** dual-writing legacy + new during a coordinated migration is a legal migration pattern (GC-010 governed migration). I considered **FP-008** and reject it: there is no incompatible contract change and the legacy topic is still valid; the harm is *stale* writes from a superseded run, which is the orphan mechanism, not an ungoverned contract break.
- **D-02 discriminator (FP-001 vs FP-012):** I considered **FP-012** (assumed-vs-provided guarantee). It is not the load-bearing route: the evidence shows an *absence* of any ownership/cancellation mechanism, not a correctness claim resting on a guarantee the model failed to provide. FP-001 is the attribution; FP-012 would only matter if there were an explicit "children die with the parent" assumption to falsify.

**Recurrence evidence:** HISTORY records a March orphan batch attributed to "bad batch data." That causal attribution is now **CONTESTED** by the current RUNTIME/CODE evidence — the same ownerless-worker mechanism fits both. I did **not** emit KNOWLEDGE_DRIFT: the March note is a historical incident diagnosis, not an accepted intent/decision record, so it does not meet the drift triggers. It is, however, a signal that the March fix did not address the real mechanism.

## Smallest safe correction

Protected property → mechanism → smallest ownership change that breaks it → compare to redesign:

1. **Give the workers an owner (T-001, supervised/structured lifecycle).** Run workers under a supervisor or OS process group that reaps children when the coordinator exits (e.g., systemd unit with kill-on-parent-exit / cgroup scope). This is the smallest structural change and covers routine coordinator restarts.
2. **Bind workers to a run epoch + liveness lease (T-002, cancellation propagation).** Each worker holds a run-epoch token and a lease that the coordinator renews; a worker refuses to write (and exits) when the lease expires or the epoch is superseded. This is the part that actually survives a hard OOM-kill, where no shutdown hook ever runs — which is exactly what happened at 03:14. The lease also encodes "which topic schema this epoch may write," so a stale worker cannot continue writing to legacy after the new consumer has started.

A wider redesign (job orchestration framework, event-sourcing rewrite, message-bus-native workers) is not the minimum: the local fix — an owner plus an epoch lease — directly breaks the orphan mechanism and protects the migration cutover. AX-004 satisfied.

## Open question (not decision-changing)

Whether the 03:20–06:00 legacy/new writes must be *repaired* depends on whether the new consumer deduplicates/idempotently consumes. That is a data-repair follow-up, not an architecture correction, and it belongs to the data/platform owner.
