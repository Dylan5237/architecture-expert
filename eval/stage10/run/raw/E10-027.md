## Decision rationale

**Mechanism (S3–S4).** This is FP-006 *Excess Privilege at Trust Boundary* under MP-005: the reporting service's duty is read (CODE: SELECT-only, verified), but its credential grants read+write on **all payments tables in all environments** (CONFIG). FP-006's causal mechanism is that granted privilege determines the action set available **after compromise *or mistake***. "No external access path" reduces attack likelihood but does not remove the boundary or the mistake path: a reporting bug, a future ORM sync feature, or a script run with the shared credential can now mutate or destroy payment records. Reporting (read-only consumer) and the payments store (critical write surface) are two deploy units with different duties — a genuine cross-privilege boundary.

**GC-012 checked, does not apply.** The good case covers *fine-grained internal trust separation demanded in a genuinely closed, same-team single deploy unit*. Here we are not demanding zero-trust granularity; we are demanding that an existing grant match the duty at a boundary that already exists. "Single company boundary" mitigates severity, but it is not a qualifier in GC-012's shape, and FP-006 fires on mistake, not only on intrusion.

**Evidence typing.** CODE answers *what reporting does*; CONFIG answers *what reporting can do*. They disagree only if conflated — the authority matrix treats them as complementary sub-questions, so this is ordinary adjudication, not `KNOWLEDGE_DRIFT`. The DBA's "can wait" and the review's "medium" (HISTORY) are triage records, not accepted intent that contradicts observed behavior.

**Severity.** HIGH_CONFIDENCE_RISK, not BLOCKER on current evidence: strong evidence + mechanism + material impact (payments integrity, all environments), but no accepted requirement artifact or established AX-003 non-negotiable is *in evidence* that this violates. Upgrade condition below.

**The DBA's deferral conflates two fixes (Q-046/Q-049).**
1. **Path fix — the minimum correction, does not need the migration ticket:** grant a SELECT-only role on the payments tables and point the reporting connection at it. Since code issues only SELECTs, this is behavior-preserving for legitimate traffic, reversible (re-grant requires a new decision), and breaks the mechanism directly. Wider options (read-only replica, network segregation) are unnecessary — a role grant already removes the write action set (AX-004).
2. **Template fix — legitimately a backlog ticket:** the 2021 template is the *replication source*; every future account minted from it inherits the same excess (including the cross-environment credential sprawl of a shared RW account). Fix the template on the planned schedule.

Deferring #1 because #2 is slow is the error: the cheap, local, reversible correction is available now and does not depend on the template migration.
