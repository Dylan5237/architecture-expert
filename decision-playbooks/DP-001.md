# DP-001 Architecture Design

## Trigger

Use when the object is a **system, slice, or capability that does not yet exist** (or exists only as intent), and the task is to propose a structure that protects required properties under named constraints.

Typical asks: “how should we structure X?”, “greenfield / new bounded context”, “what is the minimum architecture for this capability?”

## Do Not Use When

- An existing system is being judged as-is → [DP-002](DP-002.md).
- The object is a diff/PR/migration of something that already runs → [DP-003](DP-003.md).
- The object is an ADR/options paper already enumerating alternatives → [DP-004](DP-004.md) (this DP may *produce* an ADR; it does not audit one as the primary object).
- Production is failing now → [DP-005](DP-005.md) first.

## Goal

The smallest architecture that safely protects the named required properties (AX-004), with explicit non-prescriptions and no pattern-default.

## Minimum Inputs

- Intent / capability to protect.
- Required properties (even if draft) and real constraints.
- Applicable non-negotiables (AX-003: only if actually applicable).
- Who can decide trade-offs.

If properties are unnamed, stop at `NEEDS_EVIDENCE` (Q-001, Q-009) rather than inventing a fashionable shape.

## Evidence Baseline

Origins that may exist *before* code:

- PRODUCT_INTENT (required)
- USER_ASSERTION (treat as `HYPOTHESIS` until confirmed)
- ARCHITECTURE_INTENT / HISTORY if a parent system constrains the slice
- GENERIC_KNOWLEDGE for mechanism families only

CODE/CONFIG/RUNTIME of a *different* system are analogies, origin GENERIC_KNOWLEDGE unless the task says this is that system.

## Conditional Reasoning Path

1. Task class confirmed (this DP).
2. Intent & properties (Q-INT, Q-PRP). Apply AX-001. List applicable AX-003 items or explicitly none.
3. Evidence baseline: what is known vs assumed. Surface `KNOWLEDGE_DRIFT` if product intent conflicts with an inherited ADR.
4. Activate **only** dimensions implied by the shape (async work → Q-OWN; shared mutable state → Q-STA; independent consumers → Q-INTG; untrusted/agent actions → Q-TRS; saturation risk → Q-OVL; etc.). Skip the rest.
5. For each activated dimension: name the mechanism that would fail if omitted; check GC so a legal alternate form is not banned; pick the smallest intervention (T-* as *candidates*, not mandates).
6. Name 1–2 alternatives that still protect the properties. Prefer the cheaper/reversible one unless a property forbids it.
7. Close: min-sufficient proposal, OR owner trade-off, OR `ARCH_CONFLICT`. Do not tour unused domains.

Never default to microservices, event-driven, Kubernetes, DDD layers, generic workers, or caches.

## Knowledge Routes

Always: `00_ROUTER.md` → `01_CONSTITUTION.md` → this playbook.

Then **at most two** domain indexes from the overlay table in `decision-playbooks/index.md`, then only linked MP/FP/T/GC.

AX-001, AX-002, AX-004 apply to every design pass. AX-003 only when a named non-negotiable is in scope.

Do not load all ten MP pages.

## Question Sets

Always: Q-INT, Q-PRP, Q-EVD (as applicable), Q-ALT, Q-UNK.

Conditionally: Q-OWN, Q-XCN, Q-STA, Q-FLW, Q-RES, Q-OVL, Q-FAL, Q-TRS, Q-OBS, Q-INTG, Q-EVL, Q-VAL — only if step 4 activated them.

## Stop Conditions

Index stop rules 1–6, plus design-specific:

- Stop when a min-sufficient structure is named, properties mapped to mechanisms, and remaining choices are owner taste (`PERSONAL_PREFERENCE`) or documented alternatives awaiting authority.
- Stop at `NEEDS_EVIDENCE` if required properties or applicable constraints cannot be stated.

## Escalation Conditions

Index escalation list. Design-specific: irreversible storage/contract shape; trust policy for agent actions; regulatory interpretation; choosing which required property to drop.

Do not escalate “which framework” or “how many services” when properties are already protected by a simpler shape.

## Output Contract

Index shared schema. `findings` describe the **proposed structure** (not a defect list) and use `finding_disposition` only where a load-bearing class applies (e.g. PERSONAL_PREFERENCE for a taste leftover). Run-level close: `terminal_outcome` ARCH_CONFLICT if a required capability cannot be protected under stated constraints (fill `arch_conflict`); NEEDS_EVIDENCE if properties are missing; NO_DECISION_CHANGING_WORK when a min-sufficient proposal is established and nothing further can change the decision. Do not use NO_DEFECT as a finding disposition for a not-yet-built system.

## Anti-overengineering guard

AX-004 is the goal. A tactic is included only to break a named failure mechanism that the properties make relevant. If the justification is “best practice”, “scale later”, or a vendor tutorial, drop it or mark `PERSONAL_PREFERENCE`.

## Common category mistakes

- Starting from a pattern name instead of properties.
- Treating exploration as if the variation axis were already known (GC-003).
- Requiring process isolation, single-writer, a telemetry stack, or service-local shedding as universals (Constitution non-prescriptions).
- Merging resources (MP-003) with overload (MP-009) into one “scalability” move (D-04).
- Promoting P-006 change spread or H7 locality to a design principle.
- Writing a system prompt or implementation checklist into the proposal.
