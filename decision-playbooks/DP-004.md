# DP-004 Architecture Decision Review

## Trigger

Use when the object is a **named architecture decision**: ADR, RFC, options paper, or “we should choose A vs B vs C”. The task is to test whether the decision protects required properties, whether alternatives were real, and who has authority to accept the trade-off.

## Do Not Use When

- You are inventing the first structure with no decision artifact → [DP-001](DP-001.md) (that DP may emit an ADR afterwards).
- You are auditing current code as-is → [DP-002](DP-002.md) first if the ADR’s facts are unverified.
- You are reviewing a concrete PR that implements a decision → [DP-003](DP-003.md); use this DP only for the decision record itself.
- You are explaining an incident → [DP-005](DP-005.md).

If the ADR’s description of current behavior conflicts with CODE/RUNTIME, emit `KNOWLEDGE_DRIFT` and do not treat the ADR text as `CONFIRMED` current fact.

## Goal

Accept, reject, or return the decision with: properties protected, alternatives that were actually viable, reversibility, authority, and any `ARCH_CONFLICT`.

## Minimum Inputs

- The decision statement and at least the implied alternative “do nothing / status quo”.
- Required properties the decision claims to serve.
- Constraints and (if claimed) non-negotiables.
- Who is supposed to own the decision.

## Evidence Baseline

ARCHITECTURE_INTENT is the artifact itself (epistemic state: it is `CONFIRMED` that the ADR *says* X; it is not automatically `CONFIRMED` that the system *is* X).

Current behavior: CODE/CONFIG/RUNTIME if the decision depends on “we already do Y”.

PRODUCT_INTENT if the decision drops or preserves a capability.

HISTORY for previous decisions being reversed.

GENERIC_KNOWLEDGE for mechanism consequences of each option.

## Conditional Reasoning Path

1. Restate the decision as: option chosen, options rejected, properties claimed, constraints assumed (Q-INT, Q-PRP, Q-ALT).
2. Verify facts the decision stands on (Q-EVD). Drift vs code/runtime/product.
3. Activate dimensions the *options* would change (not a full-system tour). Example: choosing multi-writer → Q-STA + GC-013; choosing to skip isolation → Q-FAL + GC-005; choosing coarse trust → Q-TRS + GC-012.
4. For each rejected alternative: was it actually viable for the properties, or a straw man? What would invalidate the chosen option (Q-ALT)?
5. Reversibility and blast of committing (Q-EVL). P-005 is **not** revived as a principle; reversibility is a decision question only.
6. AX-002/AX-004: convenience is not a property. If a required capability is dropped, it is `ARCH_CONFLICT` or a product decision to escalate — not “the ADR is pragmatic”.
7. Close: accept / accept-with-conditions / `NEEDS_EVIDENCE` / owner trade-off / `ARCH_CONFLICT`.

## Knowledge Routes

`00_ROUTER.md` → `01_CONSTITUTION.md` → domains implicated by the options (usually one or two) → linked MP/FP/T/GC.

AX-001 (relative to properties), AX-002 (no silent contract shrink), AX-004 (min sufficient), AX-003 only if the ADR invokes a non-negotiable.

Do not route “decision quality” through a resurrected P-005/P-011.

## Question Sets

Always: Q-INT, Q-EVD, Q-PRP, Q-ALT, Q-UNK.

Conditional: the overlay sections that the options would change. Q-VAL if the decision claims a proof or SLA. Q-EVL for irreversibility.

## Stop Conditions

Index 1–6, plus:

- Stop when one option is uniquely required by a named property and evidence, and remaining debate is `PERSONAL_PREFERENCE`.
- Stop when two or more options still protect the properties — escalate the preference, do not invent a technical winner.
- Stop at `NEEDS_EVIDENCE` when the ADR’s factual premises are unverified.

## Escalation Conditions

Index list. Decision-specific: this DP *expects* escalation when multiple viable options remain; that is success, not incomplete work. Also: irreversible migration, trust policy, which property to drop.

Do not escalate a decision that is already uniquely determined by an applicable non-negotiable plus evidence.

## Output Contract

Index schema. `findings` evaluate **the decision**, not a hidden system review. Include rejected alternatives and what would invalidate the choice. `min_correction` here means the smallest change to the *decision* (narrower option, added bound, explicit GC/governance), not a code patch (that is DP-003).

## Anti-overengineering guard

Reject options whose only justification is future hypothetical scale, resume-driven pattern catalogs, or “industry default”. A more complex option needs a property that the simpler option cannot protect.

## Common category mistakes

- Treating ADR prose as current-behavior evidence.
- Ranking options by popularity (microservices vs monolith as identity).
- Using implementation inconvenience as `ARCH_CONFLICT`.
- Forgetting GC-003 (exploration: no stable boundary required yet).
- Forgetting D-14 (multi-writer with explicit merge is legal).
- Requiring a telemetry stack as the decision (T-014 is placement of distinguishing evidence, not a vendor).
- Turning this DP into a Stage 9 prompt (“always use RFC template…”).
