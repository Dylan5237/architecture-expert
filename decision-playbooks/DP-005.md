# DP-005 Incident Architecture Analysis

## Trigger

Use when the object is an **observed failure, near-miss, or production symptom**, and the question is whether (and which) architecture mechanism contributed — and what minimum correction breaks that mechanism.

Typical asks: retry storm, timeout cascade, stale overwrite, overload, poison-pill blast, “it worked in staging”.

## Do Not Use When

- No failure has been observed and the ask is a design or health review → [DP-001](DP-001.md) / [DP-002](DP-002.md).
- The object is a PR that has not run in anger → [DP-003](DP-003.md).
- The object is an ADR debate → [DP-004](DP-004.md).

After attribution, a follow-on “is the wider architecture sound?” is DP-002; a follow-on fix PR is DP-003. Do not smuggle those tours into this pass.

## Goal

Attribute the incident to a failure mechanism (or to a non-architecture cause), check GC so a legal form is not blamed, and name the smallest architecture/runtime correction that would have contained it. Correct result may be: not an architecture defect.

## Minimum Inputs

- Symptom and timeline (even if partial).
- The path/service/runtime-role involved (V-002-C when “service” is used).
- What “success” would have looked like (the property that broke).

If the timeline cannot distinguish two mechanisms, stop at `NEEDS_EVIDENCE` with the discriminating observation (Q-EVD, Q-OBS).

## Evidence Baseline

RUNTIME is the usual first *emphasis* for the incident timeline (not a universal origin ranking). Then CODE/CONFIG of the failing path; TEST if it pinned the wrong guarantee; PRODUCT_INTENT for impact. GENERIC_KNOWLEDGE names FP families; it never establishes what happened.

USER_ASSERTION (“it must be Kafka”) stays `claim_epistemic_state` `HYPOTHESIS` until RUNTIME/CODE ground it. That mismatch is verification, not automatic `KNOWLEDGE_DRIFT`.

## Conditional Reasoning Path

1. Name the broken property and the symptom (Q-INT, Q-PRP).
2. Evidence baseline: what is `CONFIRMED` on the timeline vs `UNKNOWN`.
3. Generate **competing mechanisms**, not a single favorite. Especially:
   - stale completion → D-02: FP-001 (no owner/cleanup) vs FP-012 (assumed ordering/cancel/clock) — both routes, not a third FP;
   - saturation → D-04: FP-003 (unbounded per-work dimension) vs FP-010 (no governed overload policy) vs FP-011 (retry amplification);
   - cascade → FP-004 vs FP-005 (coupled defense) vs overload;
   - “inconsistent” → force V-010 suffix before MP-008/FP-009.
4. Load the matching domain(s) for the surviving mechanisms only. Check GC (e.g. GC-015 path-level admission is not “missing service shedding”; GC-001 supervision is not “unowned”).
5. If architecture contributed: min correction that breaks the mechanism on this path (`terminal_outcome` MIN_SAFE_FIX_IDENTIFIED). If not: `terminal_outcome` NO_DEFECT architecturally; remaining work is ops/product.
6. Stop. Do not redesign unrelated subsystems. Do not escalate “we should rewrite”.

## Knowledge Routes

Start from the symptom → `00_ROUTER.md` need-table → one domain; add a second only for a named discriminator (D-02, D-04, D-05, D-07, D-09).

| Symptom family | First route | Second only if discriminator needs it |
|---|---|---|
| orphan, leak, no cancel, stale *without* a claimed guarantee | `lifecycle/` MP-001 FP-001 T-001 T-002 GC-001 GC-002 | `concurrency/` if a guarantee was assumed |
| assumed order/cancel/clock/isolation name | `concurrency/` MP-010 FP-012 GC-016 | `lifecycle/` if owner/cleanup is also missing |
| unbounded time/queue/retry-count/fan-out/memory | `resources/` MP-003 FP-003 T-003 T-004 T-005 GC-004 | `overload/` if the issue is *policy under saturation* |
| retry storm / admission / shedding / degradation | `overload/` MP-009 FP-010 FP-011 T-006..T-009 T-005 T-015 GC-015 | `resources/` if retry *count* is the unbounded dimension |
| cascade / shared resource / coupled defense | `reliability/` MP-004 FP-004 FP-005 T-010 GC-005 GC-006 | `security/` only for privilege (D-05); RQ5-001 not a metric to invent |
| privilege / agent action | `security/` MP-005 FP-006 T-011 GC-012 | not isolation-as-substitute |
| cannot tell states apart | `observability/` MP-006 FP-007 T-014 GC-008 | `concurrency/` if the missing thing is a *guarantee*, not a dashboard |

## Question Sets

Always: Q-INT, Q-EVD, Q-PRP, Q-OBS (what would distinguish), Q-FAL or overlay section for the surviving mechanism, Q-ALT (min correction), Q-UNK.

Do not activate every overlay “in case”.

## Stop Conditions

Index 1–6, plus:

- Stop when the incident is attributed and the min correction is clear, even if other latent risks exist (list them as out-of-scope or `NON_BLOCKING_IMPROVEMENT`).
- Stop at `terminal_outcome` NEEDS_EVIDENCE when two FPs remain and one observation would separate them — name that observation; do not average them into a BLOCKER.
- Stop with `terminal_outcome` NO_DEFECT when GC applies or the cause is not architectural.

## Escalation Conditions

Index list. Incident-specific: drop a product capability to restore stability (AX-002); trust-boundary change under pressure; irreversible data repair.

Do not escalate “need more microservices so this never happens”. Do not escalate a clear timeout/owner/admission fix.

## Output Contract

Index schema. Timeline facts use origin RUNTIME with a typed `claim_epistemic_state`. `findings` must include competing mechanisms considered and why they were dropped, and must use `finding_disposition` (not NO_DEFECT/ARCH_CONFLICT). `min_correction` is the containment for *this* failure path. BLOCKER/HIGH_CONFIDENCE_RISK include `refutation_or_invalidation`.

## Anti-overengineering guard

Incidents attract rewrites. The default is: restore an owner, a bound, a failure-domain cut, an admission point, an explicit conflict rule, or distinguishing evidence — whichever breaks the named mechanism. Broader redesign only if that local fix cannot protect the property (AX-004 + minimum-correction rule).

## Common category mistakes

- One-symptom-one-pattern (retry → “use circuit breaker node”; Constitution omitted that buzzword node).
- Merging D-02 into “async is dangerous”.
- Treating missing dashboards as FP-007 when the needed question is already proved (GC-008) or when the gap is an assumed guarantee (FP-012).
- Inventing a blast-radius SLO (RQ5-001).
- Blaming coarse trust during a crash with no trust-boundary involvement (GC-012 / D-05).
- Continuing into a full DP-002 tour “while we have the pager”.
