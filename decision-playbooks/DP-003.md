# DP-003 Change / PR Architecture Review

## Trigger

Use when the object is a **delta**: pull request, migration, config/flag change, API change, or “we will start doing X this way”. The question is whether the *change* preserves required properties and which minimum correction (if any) the delta needs.

## Do Not Use When

- There is no existing baseline to diff against → [DP-001](DP-001.md).
- The ask is a full as-is review of a system, not of a change → [DP-002](DP-002.md).
- The change is already a production incident → [DP-005](DP-005.md) until the failure is attributed.
- The artifact is an options/ADR document rather than a concrete change → [DP-004](DP-004.md).

## Goal

Accept, reject, or qualify the delta against required properties. Prefer a local fix to the delta over a system rewrite (minimum-correction rule).

## Minimum Inputs

- The delta (diff, migration plan, or precise behavioral change).
- Surrounding invariants: contracts, owners, bounds, trust boundaries the delta can touch.
- Required properties for the path being changed.

## Evidence Baseline

Primary origins: CODE/CONFIG/TEST of the delta **and** of the unchanged neighbors it can affect; PRODUCT_INTENT for what must not break; ARCHITECTURE_INTENT if an ADR constrains the change; RUNTIME if the PR includes prod evidence.

GENERIC_KNOWLEDGE explains how a delta can create FP-* mechanisms. It does not invent neighboring facts the diff does not show — that is `NEEDS_EVIDENCE`, not automatic `KNOWLEDGE_DRIFT`.

## Conditional Reasoning Path

1. Name the delta and the properties it must preserve (Q-INT, Q-PRP).
2. Evidence baseline: what the diff actually does vs what reviewers were told. If an accepted ADR/PRODUCT_INTENT disagrees with the delta, emit `KNOWLEDGE_DRIFT`. An unverified commit message vs code is verification (Q-004/Q-007), not automatic drift.
3. Blast *of this delta* (who else must change, which consumers, which failure domain). This is not P-006-as-principle; spread is a review signal (Q-EVL) and a contract question (Q-INTG) when consumers are independent.
4. Activate overlays only for mechanisms the delta can introduce (new retry → Q-OVL; new async completion → Q-OWN+Q-XCN; new writer → Q-STA; new privilege → Q-TRS; new bound removed → Q-RES).
5. GC before defect: governed breaks (GC-009..011), exploration (GC-003), path-level controls (GC-015), etc.
6. Minimum correction **to this delta** first. Widen only if the local fix cannot protect the property.
7. Stop. Unrelated pre-existing smells are out of scope unless the delta makes them newly load-bearing — then mark `NON_BLOCKING_IMPROVEMENT` or hand to DP-002 explicitly.

## Knowledge Routes

Same overlay table as DP-002, but scoped to the delta.

Always consider Q-INTG when the delta publishes or breaks a contract, and Q-EVL when it moves a change-decision boundary.

Compatibility direction: T-012. Do not load expand-contract (RQ3-006 omitted). Internal churn vs independent consumers: GC-011.

## Question Sets

Always: Q-INT, Q-EVD, Q-PRP, Q-ALT (min correction), Q-INTG if any consumer exists, Q-UNK.

Conditional: overlay sections from the index. Q-EVL when the delta changes module/decision boundaries. Q-VAL when the delta claims a proof or drops evidence.

## Stop Conditions

Index 1–6, plus:

- Stop when the delta has `terminal_outcome` NO_DEFECT relative to properties, even if the rest of the system is imperfect.
- Stop when a min correction to the delta is clear (BLOCKER/MUST_FIX finding on the delta; `terminal_outcome` MIN_SAFE_FIX_IDENTIFIED).
- Stop at `terminal_outcome` NEEDS_EVIDENCE when neighbor behavior the delta depends on is not in the diff and not otherwise evidenced.

## Escalation Conditions

Index list. Change-specific: irreversible migration; independent-consumer break without a governing higher-priority requirement; trust-boundary expansion; cross-team contract.

Do not escalate nits, formatting, or “please add an extra service”.

## Output Contract

Index schema. Findings must say whether they apply to **the delta** or are explicitly out-of-scope carry-overs, and must use `finding_disposition` (not NO_DEFECT/ARCH_CONFLICT). `min_correction` should be expressible as a change to this PR/plan when a BLOCKER exists. BLOCKER/HIGH_CONFIDENCE_RISK include `refutation_or_invalidation`. `terminal_outcome` NO_DEFECT for a clean delta; MIN_SAFE_FIX_IDENTIFIED when the min patch is clear; ARCH_CONFLICT only as the run-level terminal with its record.

## Anti-overengineering guard

Do not use a PR review to introduce microservices, a new platform, or a rewrite. If the delta is locally unsafe, the default recommendation is the smallest patch that restores the bound/owner/contract/evidence. AX-004 applies to the *resulting* system, not to “while we’re here”.

## Common category mistakes

- Reviewing the whole monolith because a one-line timeout changed.
- Treating any compatibility break as FP-008 without independent consumers or governance (GC-009..011).
- Treating wide-but-coherent migration as a locality violation (GC-007 / P-006).
- Demanding service-local shedding when the path already admits at the gateway (GC-015).
- Retry added without asking T-015 (retry ≠ idempotency).
- Silent product-contract shrink to make the PR smaller (AX-002) — that is `terminal_outcome` ARCH_CONFLICT (with record) or a BLOCKER finding, not “pragmatic”.
